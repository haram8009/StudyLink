# StudyLink 1일차 PRD — PDF에서 근거 답변까지

작성일: 2026-10-21 (Asia/Seoul)  
상태: 사용자 구현 지시에 따라 실행한 1일차 요구사항. 핵심 흐름·자동 테스트·통합 확인을 마쳤고 사람 평가 등 남은 인수 항목은 통합 기록을 따른다.  
후속: 사용자 지시로 3개 담당 에이전트가 구현에 착수했으며, [1일차 확인 결과·남은 작업](day1-integration.md)을 별도로 기록했다. 아래 체크리스트는 당초 인수 계획으로 보존한다.  
기준: [구현기획서 v1.1](studylink-implementation-plan-v1.1.md) 0·6·7·9·10·13절, [아키텍처](studylink-architecture.md) 3·4·6·8·12절, [ADR 0001](adr/0001-langgraph-without-langchain.md), [도메인 용어집](../CONTEXT.md).

## Problem Statement

학습자는 PDF 자료에서 질문의 답을 찾고, 답변이 어느 페이지에 근거하는지 확인하고 싶다. 답변만 제공하거나 근거 없는 문장을 섞으면 학습자가 원문과 대조하기 어렵다. 자료가 처리 중인지, 질문의 근거가 부족한지, 외부 서비스가 실패했는지도 구별할 수 있어야 한다.

3일·3명 시제품의 첫날에는 프런트·백엔드·에이전트가 각각 동작하는 것만으로 부족하다. 실제 PDF 한 개를 업로드하고 검색 가능한 상태로 만든 뒤, 질문에 대한 페이지 인용 답변을 한 화면에서 확인하는 흐름을 통합해야 한다. 이 흐름이 둘째 날 노트 저장·연결과 셋째 날 복습 기능의 기반이 된다.

## Solution

로컬 단일 사용자 앱에서 워크스페이스를 만들고 텍스트 PDF를 업로드한다. 처리 상태를 확인한 뒤 질문하면 해당 워크스페이스 자료에서 찾은 근거만으로 답변을 보여준다. 각 답변 문장의 인용에 자료와 페이지를 표시하며, 근거가 부족하면 “자료에서 확인하지 못함”으로 보류한다.

**첫날 필수 통합 결과는 PDF 업로드 → ready → 질문 → 페이지 인용 답변이다.** 인용 클릭을 통한 PDF 패널 페이지 이동 완성은 기존 일정의 2일 오전에 둔다. 첫날에는 반환된 자료 ID·페이지·발췌가 원문과 일치하는지 확인한다.

목 데이터로 화면을 먼저 만들되, 종료 점검은 실제 수집·검색·답변 경로로 한다. 목 모드 통과와 실제 GMS 통합 통과를 별도로 기록한다.

## User Stories

1. 학습자로서, 과목이나 학습 목표별 워크스페이스를 만들고 싶다. 자료의 검색 범위를 구분하기 위해서다.
2. 학습자로서, 워크스페이스의 제목과 목표를 저장하고 싶다. 나중에 학습 맥락을 다시 확인하기 위해서다.
3. 학습자로서, 기존 워크스페이스 목록과 상세를 열고 싶다. 업로드한 자료가 있는 곳으로 돌아가기 위해서다.
4. 학습자로서, 선택한 워크스페이스에 텍스트 PDF를 업로드하고 싶다. 내 자료를 질문의 근거로 사용하기 위해서다.
5. 학습자로서, 자료의 processing·ready·failed 상태를 보고 싶다. 질문 가능한 시점을 알기 위해서다.
6. 학습자로서, 처리 실패 사유를 보고 재시도하고 싶다. 자료를 처음부터 다시 등록하지 않고 복구하기 위해서다.
7. 학습자로서, 서버 재시작으로 중단된 자료가 실패 상태로 표시되길 원한다. 끝나지 않는 처리를 기다리지 않기 위해서다.
8. 학습자로서, PDF가 아니거나 지원하지 않는 자료를 올렸을 때 안내받고 싶다. 입력을 수정하기 위해서다.
9. 학습자로서, 현재 워크스페이스의 자료에 대해 질문하고 싶다. 다른 과목 자료가 답변에 섞이지 않도록 하기 위해서다.
10. 학습자로서, 아직 검색할 자료가 없을 때 이유를 알고 싶다. 처리 완료를 기다릴지 자료를 추가할지 판단하기 위해서다.
11. 학습자로서, 질문 처리 중 진행 표시를 보고 싶다. 응답을 기다리는 동안 중복 요청하지 않기 위해서다.
12. 학습자로서, 답변의 각 문장에 유효한 답변 인용을 보고 싶다. 어떤 근거에서 나온 설명인지 확인하기 위해서다.
13. 학습자로서, 답변 인용의 자료명·페이지·발췌를 확인하고 싶다. 원문과 답변을 직접 대조하기 위해서다.
14. 학습자로서, 근거가 없는 문장은 표시되지 않길 원한다. 확인되지 않은 설명을 학습하지 않기 위해서다.
15. 학습자로서, 자료로 답할 수 없는 질문에는 근거 부족 안내를 받고 싶다. 자료가 설명하는 범위를 알기 위해서다.
16. 학습자로서, 외부 서비스 장애와 근거 부족을 구분하고 싶다. 잠시 후 다시 질문할지 판단하기 위해서다.
17. 학습자로서, 질문 실패 후 입력 내용이 유지되길 원한다. 같은 질문을 다시 작성하지 않기 위해서다.
18. 학습자로서, 앱을 재시작해도 워크스페이스와 처리 완료 자료가 유지되길 원한다. 학습 준비를 반복하지 않기 위해서다.
19. 개발 팀원으로서, 첫 2시간 안에 HTTP·내부 함수 계약을 합의하고 싶다. 서로의 구현을 기다리지 않고 개발하기 위해서다.
20. 개발 팀원으로서, 외부 모델 없이 정상·출력 오류·통신 실패를 재현하고 싶다. 오류 흐름을 반복 확인하기 위해서다.
21. 개발 팀원으로서, 검색 근거와 생성 결과를 하나의 질문 trace로 확인하고 싶다. 잘못된 답변이 검색과 생성 중 어디에서 발생했는지 찾기 위해서다.
22. 개발 팀원으로서, 관측 서비스가 실패해도 질문 기능을 사용하고 싶다. 계측 문제로 통합 시연이 중단되지 않도록 하기 위해서다.
23. 개발 팀원으로서, 실제 임베딩과 목 임베딩을 분리하고 싶다. 테스트 데이터가 실제 검색 결과를 오염시키지 않도록 하기 위해서다.
24. 개발 팀원으로서, 빈 환경에서 같은 의존성으로 앱을 실행하고 싶다. 다른 팀원의 환경에서도 첫날 통합 결과를 재현하기 위해서다.

## Implementation Decisions

### 기존 확정 사항

- 별도 새 저장소와 새 Python·프런트 패키지 환경에서 시작한다. 현재 실습 코드·의존성·가상환경을 재사용하지 않는다.
- React 18·Vite·JavaScript, FastAPI, SQLite, PyMuPDF, numpy, LangGraph, httpx 기반 GMS 어댑터, Langfuse 직접 계측을 사용한다. 애플리케이션에서 LangChain을 직접 사용하지 않는다.
- Vite의 `/api` 프록시로 FastAPI에 연결한다. FastAPI는 단일 worker와 동기 엔드포인트를 사용한다.
- 첫날 전체 HTTP 계약과 내부 함수 계약을 합의하되, 전체 기능을 첫날 구현하는 것으로 해석하지 않는다.
- DB에는 전체 시제품의 스키마를 준비한다. 첫날 업무 흐름은 워크스페이스·자료·청크·답변을 사용한다. 노트 원본과 워크스페이스의 연결은 별도 관계라는 설계를 유지한다.
- SQLite는 WAL과 외래 키 검사를 켜고, 요청과 수집 작업의 연결을 분리한다. 외부 호출 중에는 쓰기 트랜잭션을 유지하지 않는다.

### 모듈 경계 제안

| 모듈 | 단순한 외부 계약 | 내부에 감추는 책임 | 담당 |
| --- | --- | --- | --- |
| 학습 화면·API 클라이언트 | 워크스페이스 선택, 업로드, 질문, 답변 표시 | 목 응답 전환, 폴링, 로딩·오류 상태 | A |
| 워크스페이스·자료 저장 서비스 | 생성·목록·상세·자료 조회 | SQLite 접근, ID, 영속화와 상태 조회 | B |
| 자료 수집 | `ingest_document(document_id)` | 추출·반복 머리말/꼬리말 제거·페이지 청킹·배치 임베딩·상태 전이 | B 주도, C와 임베딩·청킹 계약 공동 |
| 근거 검색 | `retrieve(workspace_id, query, include_notes)` | 범위 제한, 모델 일치 검사, 코사인 계산, 근거 선택 | C |
| 답변 서비스·그래프 | `answer_question(workspace_id, question, include_notes)` | 검색·생성·인용 검증·보류와 결과 저장 경계 | C 그래프, B 저장·HTTP 연결 |
| GMS 어댑터 | `embed(texts)`, `generate_json(prompt, schema)` | 인증·HTTP·구조화 출력 파싱·통신 오류 분류·목 응답 | C |
| 관측 어댑터 | 요청·노드·모델 호출 계측 | trace 연결, 사용량·지연 기록, 관측 장애 격리 | C |

수집·검색·답변·GMS 어댑터는 내부 단계마다 서비스를 쪼개기보다 위 계약 아래 구현을 묶는다. 테스트는 계약의 결과와 오류를 관찰한다. 노트 색인·초안·퀴즈는 후속 계약만 확보하고 첫날 실제 기능으로 확장하지 않는다.

### 자료 수집과 검색

- 업로드는 자료를 저장하고 processing으로 응답한 뒤 BackgroundTasks로 수집한다. 청크 저장과 ready 변경은 한 트랜잭션으로 완료한다. 실패 시 failed와 사유를 남긴다.
- 페이지 번호는 1부터 시작한다. 청크는 페이지 경계를 넘지 않으며 긴 페이지는 약 800자로 나눈다. 여러 페이지에 반복되는 제목·쪽 번호 머리말/꼬리말을 제거한다.
- processing 자료만 2초 간격으로 폴링한다. 서버 시작 시 남은 processing은 “서버 재시작으로 중단” 사유로 failed 처리하고 retry API로 재수집한다.
- 검색 전에 현재 워크스페이스의 ready 자료만 후보로 제한한다. 임베딩 모델·차원이 다른 벡터는 섞지 않는다. 연결 노트 검색의 계약은 유지하되 실제 통합은 2일차다.
- 근거는 최소 점수, 최고 점수 대비 상대 기준, 최대 12개·약 8,000자 상한 순으로 선택한다. 기준값의 품질 보정은 2일차다. 최소 점수를 통과한 노트 1개 보장 규칙도 노트 검색 통합 때 적용한다.
- 모델 교체 시 전체 자료·노트를 재수집하는 관리 스크립트는 기존 점검 문서의 1일차 후속 작업이다. 첫날은 자료 재수집 경로를 준비하고, 노트 재색인은 노트 구현 시 연결한다. 두 범위의 완료 여부를 따로 기록한다.

### 답변과 오류 계약

- 답변은 `answer_id`, `status`, `segments`, `citations`를 반환한다. status는 grounded 또는 insufficient_evidence다. 모델은 근거 ID만 생성하고 자료 ID·페이지·발췌는 서버가 검색 근거에서 채운다.
- 제공되지 않은 인용 ID를 제거하고, 유효 인용이 없는 segment는 표시하지 않는다. 첫날에는 정상 생성·인용 검증·근거 부족 보류를 통합한다.
- 재검색 최대 1회와 출력 재생성 최대 1회, 제거된 segment가 절반을 넘을 때 재생성하는 최종 정책은 기존 설계를 유지한다. 첫날에는 최소 그래프와 목 시나리오로 종료·재시도 소진을 검증하고, 실제 답변 그래프의 재검색·재시도 완성은 2일 오전에 수행한다. 첫날의 임시 검증 실패 처리는 보류이며 최종 정책 완료로 보고하지 않는다.
- 범위 내 후보 자체가 없으면 400으로 처리 중 자료 유무를 구분해 안내한다. 후보는 있으나 답할 근거가 없으면 200 + insufficient_evidence다. 공급자 장애는 503, 내부 그래프 실행 오류는 500이며 근거 부족으로 위장하지 않는다.
- GMS 기본 모델은 gpt-4.1-mini, 임베딩은 text-embedding-3-small이다. Pydantic으로 출력을 검증한다. 출력 오류와 공급자 통신 오류를 구별한다.
- 통신 타임아웃은 20초, 질문 요청 전체 한도는 30초다. 일시적 통신 오류만 1회 재시도하며 남은 요청 시간을 넘기지 않는다. 질의응답 10초는 목표이며 보장이나 첫날 실측 결과가 아니다.
- 답변 결과는 그래프 종료 후 서비스에서 저장한다. 재시도 노드 안에서 DB를 쓰지 않는다. 최근 답변·단건 조회 계약은 고정하되 화면 복구 통합은 후속 일정에 둔다.

### 첫날 구현할 HTTP 범위

| 기능 | 계약 |
| --- | --- |
| 워크스페이스 | `GET/POST /api/workspaces`, `GET /api/workspaces/{id}` |
| 자료 업로드 | `POST /api/workspaces/{id}/documents` |
| 자료 상태·재시도 | `GET /api/documents/{id}`, `POST /api/documents/{id}/retry` |
| 원문 제공 | `GET /api/documents/{id}/file` — PDF inline 응답, 후속 페이지 이동의 기반 |
| 질문 | `POST /api/workspaces/{id}/ask` — question, include_notes 입력 |

오류 응답은 기존 `detail` 계약을 사용한다. 업로드 크기 제한(기존 예시 30MB)과 스캔 PDF 판정 기준은 첫 2시간 계약 합의에서 확정할 값이며, 이미 확정된 수치처럼 취급하지 않는다.

### 목 모드와 관측

- 프런트 목 모드와 서버 `MOCK_LLM=1`을 구분한다. 서버 목 모드는 그래프 구조를 유지하고 어댑터 응답만 바꾼다. 목 DB와 실제 임베딩 DB를 분리한다.
- 첫날은 `ask` 요청의 그래프·노드·모델 호출을 Langfuse에 연결한다. 선택 근거·점수, 프롬프트·응답, 모델, 지연, 공급자가 반환한 토큰 사용량을 기록한다. 초안·퀴즈 trace는 각 기능 구현 때 추가한다.
- 계측 장애는 no-op으로 전환하되 업무 예외를 삼키지 않는다. 비밀키는 환경 설정에만 두고 문서·로그에 남기지 않는다.
- 데모 PDF 2개의 발췌를 Langfuse JP 리전에 저장하는 기존 허용 범위만 사용한다.

## Testing Decisions

아래 자동 테스트 범위는 사용자 확인 전 제안이다. 좋은 테스트는 내부 함수 호출 순서나 SQL 문장을 복제하지 않고, 공개 계약의 반환값·상태 변화·저장 결과·오류 구분을 검증한다. 실제 모델의 문구나 임의의 유사도 수치에 기대지 않는다.

| 대상 | 제안 검증 | 방식 |
| --- | --- | --- |
| 자료 수집 | 페이지 경계·번호 보존, ready 전환, 실패 사유, 실패 시 검색 가능한 부분 청크 미노출, 재시작 중단·재수집 | 작은 텍스트 PDF와 임시 DB, 임베딩 대역 |
| 근거 검색 | 다른 워크스페이스·미완료 자료·다른 임베딩 모델 제외, 상한 준수, 후보 없음 | 고정 벡터와 임시 DB |
| 답변 검증·그래프 | 무효 ID·무인용 문장 미노출, 근거 부족, 통신 실패 구분, 최소 그래프의 유한 종료 | 고정 모델 출력과 실패 시나리오 |
| GMS 어댑터 | 구조화 출력 검증, 인증 오류 즉시 실패, 일시 오류 재시도 한도, 시간 예산 | HTTP 대역, 실제 호출은 별도 smoke 확인 |
| 관측 어댑터 | 계측 실패에도 답변 유지, 업무 예외는 보존 | 계측 대역과 수동 trace 확인 |
| HTTP·화면 통합 | 업로드부터 인용 답변까지 연결, 오류 안내와 질문 입력 유지 | 실제 앱에서 수동 인수 점검 |

기존 테스트 선례: 현재 작업 폴더에서 StudyLink 제품 코드·제품 테스트를 확인하지 못했다. 새 제품 환경을 만드는 계획이며 실습 테스트를 재사용하지 않는다. 아키텍처에 기록된 GMS·LangGraph·Langfuse·PDF 사전 검증은 연결 가능성에 대한 참고 결과이고, 제품 회귀 테스트를 대신하지 않는다.

첫날 인수 기준:

- [ ] 빈 환경에서 설치·실행되고 검증한 의존성 버전이 고정되어 있다.
- [ ] 워크스페이스를 생성한 뒤 재시작해도 목록·상세에서 조회된다.
- [ ] 워드 임베딩 데모 PDF 업로드 후 processing에서 ready로 전환되고, 재시작 후에도 자료·청크가 유지된다.
- [ ] “Vanishing gradient가 뭐야?” 질문에 페이지 인용 답변을 받고, p.3 원문이 주장을 뒷받침하는지 사람이 확인한다.
- [ ] 답변의 모든 표시 segment에 실제 제공된 근거 인용이 있고 자료 ID·페이지·발췌가 서버 근거와 일치한다.
- [ ] 자료에 없는 질문이 근거 부족으로 보류된다. 공급자 실패는 별도 오류로 표시된다.
- [ ] 빈 워크스페이스·처리 중·수집 실패·재시작 중단 안내와 재시도 경로를 확인한다.
- [ ] 목 시나리오로 출력 오류·통신 오류·최소 그래프의 재시도 소진을 확인한다.
- [ ] 실제 GMS를 사용한 전체 흐름과 Langfuse ask trace를 확인한다. 목 모드 통과만으로 체크하지 않는다.
- [ ] 담당자·실행 환경·입력·결과·남은 실패를 기록한다. 실제 기능과 목 검증 결과를 구분한다.

15개 평가 질문의 전체 합격률, 노트 인용 품질, 퀴즈 정확도는 2~3일차 평가이며 첫날 달성했다고 보고하지 않는다.
