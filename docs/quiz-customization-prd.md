# StudyLink PRD — 퀴즈 설정·요청 개수 충족·해설 참고 자료

작성일: 2026-10-22 (Asia/Seoul)  
수정일: 2026-10-22 (Asia/Seoul)  
상태: 설정·API·저장·보충 그래프·참고 자료 표시를 구현했다. 1~10문항·기본 5, 세 난이도·기본 보통, 5라운드·120초 기본안을 초기 구현값으로 채택했다. 검증 결과와 미완료된 사람 품질 검토는 [변경 통합 기록](quiz-customization-integration.md)에 구분해 기록한다. 아래 기본안의 설명은 결정 당시 제안 근거를 보존한다.  
기준: [용어집](../CONTEXT.md), [구현기획서 v1.1](studylink-implementation-plan-v1.1.md), [아키텍처](studylink-architecture.md), [3일차 PRD](studylink-day3-prd.md), [퀴즈 구현 기록](day3-quiz-agent.md), [ADR 0001](adr/0001-langgraph-without-langchain.md).

이 문서는 기존 문서의 **5문항 고정·실패 문항 제외 후 부분 생성 성공** 정책을 대체하는 변경 요구사항이다. 기존 구현 기록은 당시 동작의 기록으로 보존한다. 구현 결과는 위 통합 기록을 따른다.

## Problem Statement

학습자는 복습에 쓸 시간과 이해 수준에 맞춰 문항 수와 난이도를 정하고 싶다. 현재 화면은 항상 5문항을 요청하며 서버 입력도 1~5문항으로 제한된다. 난이도 선택·전달·저장은 없다. 문항이 검증에서 탈락하면 한 번만 재생성하고, 계속 실패한 문항은 제외한 채 남은 문항으로 퀴즈를 완료한다. 따라서 사용자가 의도한 학습량을 보장하지 못한다.

정답·해설을 읽을 때는 어떤 자료의 어디를 다시 읽어야 하는지 바로 알아야 한다. 현재 문항 상단에 자료명·페이지와 원문 열기 기능이 있고, 채점 응답에도 자료 ID·자료명·페이지·인용문이 있다. 하지만 해설 영역에는 해설과 인용문만 있어 참고할 자료의 위치가 분명하게 묶여 보이지 않는다. 데이터가 없는 문제가 아니라 해설 맥락에서 다시 제시할 필요가 있는 문제다.

## Solution

퀴즈를 만들기 전에 문항 수와 난이도를 선택한다. 시스템은 그 설정으로 문항을 생성·검증하고, 통과한 문항은 보존하면서 부족한 수만 추가 생성한다. **새 퀴즈는 검증된 문항 수가 요청한 문항 수와 정확히 같을 때만 저장·제시한다.** 탈락 문항이나 동일 문항 복사로 개수를 채우지 않는다.

채점 후 각 문항의 정답·해설 바로 아래에 ‘참고 자료’를 두고 자료명·페이지·근거 인용문과 원문 이동을 함께 제공한다. 맞힌 문항과 틀린 문항 모두 동일하게 표시하고 오답 상세에도 같은 규칙을 적용한다.

공급자 장애나 계속되는 검증 실패에서는 생성 완료를 보장할 수 없다. 이 경우 재시도 예산 안에서 보충하고, 소진하면 부족한 퀴즈를 성공으로 내보내지 않고 실패와 다음 행동을 안내한다.

## User Stories

1. 학습자로서, 퀴즈 생성 전에 원하는 문항 수를 선택하고 싶다. 복습 시간을 조절하기 위해서다.
2. 학습자로서, 난이도를 선택하고 싶다. 현재 이해 수준에 맞는 복습을 하기 위해서다.
3. 학습자로서, 각 난이도의 설명을 보고 싶다. 어떤 유형의 문제가 나올지 예상하기 위해서다.
4. 학습자로서, 선택한 문항 수와 난이도를 확인한 뒤 생성하고 싶다. 잘못된 설정으로 시작하지 않기 위해서다.
5. 학습자로서, 어느 생성 버튼을 눌러도 같은 설정이 적용되길 원한다. 진입 위치에 따라 결과가 달라지지 않게 하기 위해서다.
6. 학습자로서, 요청한 수와 정확히 같은 수의 문항을 받고 싶다. 계획한 학습량을 채우기 위해서다.
7. 학습자로서, 탈락 문항은 자동으로 다시 만들어지길 원한다. 직접 여러 번 생성할 필요를 줄이기 위해서다.
8. 학습자로서, 이미 검증된 문항은 유지되길 원한다. 보충 생성 때문에 전체 퀴즈가 계속 바뀌지 않게 하기 위해서다.
9. 학습자로서, 같은 문제를 반복해서 받지 않길 원한다. 개수만 채운 퀴즈를 피하기 위해서다.
10. 학습자로서, 선택한 난이도가 보충 생성에도 유지되길 원한다. 끝부분의 문제만 쉬워지지 않게 하기 위해서다.
11. 학습자로서, 모든 문항이 워크스페이스의 처리 완료 자료를 근거로 하길 원한다. 자료 밖의 사실을 외우게 되지 않기 위해서다.
12. 학습자로서, 생성과 검증·보충이 진행 중임을 알고 싶다. 요청을 불필요하게 반복하지 않기 위해서다.
13. 학습자로서, 연속 클릭으로 여러 퀴즈가 만들어지지 않길 원한다. 중복 생성을 막기 위해서다.
14. 학습자로서, 생성에 실패하면 설정을 유지한 채 다시 시도하고 싶다. 처음부터 설정하지 않기 위해서다.
15. 학습자로서, 자료 부족·검증 실패·모델 장애를 구분한 안내를 받고 싶다. 다음 행동을 판단하기 위해서다.
16. 학습자로서, 목록과 퀴즈 상세에서 생성 설정을 확인하고 싶다. 이전 복습을 구분하기 위해서다.
17. 학습자로서, 새로고침 후에도 문항과 생성 설정이 복구되길 원한다. 이어서 풀기 위해서다.
18. 학습자로서, 제출 전에는 정답·해설·정답을 드러내는 인용문이 보이지 않길 원한다. 스스로 풀기 위해서다.
19. 학습자로서, 채점 후 맞힌 문항에서도 참고 자료를 보고 싶다. 정답의 이유를 다시 확인하기 위해서다.
20. 학습자로서, 틀린 문항의 해설에서 자료명과 페이지를 바로 보고 싶다. 다시 공부할 위치를 찾기 위해서다.
21. 학습자로서, 참고 자료를 누르면 해당 PDF 페이지가 열리길 원한다. 수동으로 페이지를 찾지 않기 위해서다.
22. 학습자로서, 해설을 뒷받침하는 원문 일부를 보고 싶다. 설명과 근거를 비교하기 위해서다.
23. 학습자로서, 오답 상세에서도 같은 참고 자료를 보고 싶다. 나중에 복습할 때 원문을 찾기 위해서다.
24. 학습자로서, 원문을 열 수 없어도 저장된 해설과 인용문을 읽고 싶다. 이전 학습 기록을 활용하기 위해서다.
25. 학습자로서, 예전에 만든 퀴즈도 계속 열고 제출할 수 있길 원한다. 새 기능 때문에 기존 기록을 잃지 않기 위해서다.

## Implementation Decisions

### 1. 범위와 모듈 경계

사용자 확인(2026-10-22): 변경 모듈은 다음 세 영역으로 나눈다. 자동 테스트는 생성·검증과 API·저장에 집중한다.

| 모듈 | 책임 | 외부 계약 |
| --- | --- | --- |
| 퀴즈 설정 화면·API·저장 | 설정 입력·검증·전달, 생성 잠금, 완성 결과의 원자적 저장, 설정 복원 | 문항 수·난이도를 받아 완성된 퀴즈 또는 명시적 실패를 제공 |
| 요청 개수를 채우는 생성·검증 | 근거 선택, 난이도별 출제, 문항·근거·중복 검증, 부족분 보충, 종료 판단 | 워크스페이스·문항 수·난이도 입력 → 정확한 수의 유효 문항 또는 유형별 실패. DB 저장 없음 |
| 정답·해설의 참고 자료 표시 | 자료명·페이지·인용문·원문 이동과 열람 불가 상태 | 기존 문항의 근거 정보를 받아 퀴즈 결과와 오답 상세에서 동일하게 표시 |

생성 정책은 두 번째 모듈 안에 모은다. 화면과 HTTP 라우터는 보충 횟수·근거 교체·중복 제거를 각각 구현하지 않는다. LangGraph StateGraph·Send, GMS 직접 어댑터, Langfuse 직접 계측과 기존 계층 경계를 유지한다.

### 2. 문항 수·난이도 기본안

아래 값은 사용자에게 확정받은 수치가 아니라 이번 PRD의 권장 기본안이다. 다른 값을 채택하면 UI·API·예산·테스트를 함께 맞춘다.

| 설정 | 기본안 | 동작 |
| --- | --- | --- |
| 문항 수 | 정수 1~10, 기본 5 | 입력 범위와 API 범위를 일치시킨다. 범위 밖·소수·문자열·불리언은 422로 거절하고 자동 보정하지 않는다 |
| 난이도 | 쉬움·보통·어려움, 기본 보통 | API 값은 easy·medium·hard. 다른 값은 422 |
| 쉬움 | 명시된 개념·용어·사실 확인 | 근거에서 정답을 직접 찾을 수 있게 출제 |
| 보통 | 원리·관계·차이 이해 | 근거에 서술된 관계를 설명·비교하게 출제 |
| 어려움 | 조건에 따른 적용·판단 | 근거 안에서 결론을 도출할 수 있는 상황을 제시. 외부 지식을 요구하거나 문장을 모호하게 만들어 난이도를 높이지 않음 |

난이도는 퀴즈 전체에 적용하며 보충 문항에도 전달한다. 최초 출제·검증 실패 보정·중복 대체에 같은 기준을 적용한다. 코드가 난이도의 교육적 적절성을 완전히 판정한다고 가정하지 않는다. 프롬프트 전달은 자동 테스트로, 실제 난이도와 정답·해설 품질은 사람 검토로 확인한다.

설정은 생성 버튼 앞에 항상 보인다. 빈 화면과 목록의 생성 버튼이 하나의 설정 상태를 사용한다. 생성 중에는 설정과 버튼을 비활성화하고, 실패하면 선택값을 유지한다. 목록·상세에는 문항 수와 난이도를 표시한다. 기존 ‘서로 다른 페이지에서 5문항’, ‘정상 5문항’ 같은 고정 문구와 목 데이터도 설정에 맞춘다.

### 3. 정확한 개수 충족과 보충 생성

새 퀴즈 생성 성공의 불변 조건은 requested_count = actual_count = 저장 문항 수 = 응답 문항 수다. 생성 서비스뿐 아니라 저장 직전에도 검사하여 부분 결과가 다른 경로로 저장되지 않게 한다.

1. 현재 워크스페이스의 ready 자료에서 기존 최소 길이 기준을 충족하는 문서 청크를 후보로 선택한다. 노트·다른 워크스페이스·처리 중 자료는 제외한다.
2. 요청한 문항 수만큼 출제 슬롯을 만든다. 후보 근거 수를 슬롯 수의 상한으로 삼지 않는다. 서로 다른 자료·페이지를 우선 사용한다.
3. 각 슬롯에서 설정한 난이도로 문항을 생성하고 기존 JSON·선택지·정답·해설 검증과 서버의 근거 유효성 검사를 수행한다. 구조 또는 문항 검증 실패는 오류 사유를 전달해 1회 재생성한다.
4. 부모 취합 단계에서 통과 문항을 보존한다. 문제와 선택지의 공백·대소문자·선택지 순서를 정규화한 동일 문항은 한 개만 인정한다. 최소한의 동일 문항 방지이며 의미상 유사한 모든 문제를 탐지한다는 보장은 아니다.
5. 부족하면 부족한 슬롯만 다음 라운드에 보낸다. 실패 슬롯의 근거는 다른 적합한 근거로 교체하는 것을 우선한다. 같은 근거를 재사용할 때는 다른 학습 포인트를 요구하고, 이미 채택한 문항의 문제·선택지를 중복 회피 정보로 전달한다.
6. 정확히 요청 수를 채우면 선택지를 섞고 정답 ID를 일관되게 다시 매긴 뒤 반환한다. 초과 후보가 생기면 요청 수만 확정한다.
7. 예산이 소진되면 전체 요청을 실패 처리한다. 검증 기준을 낮추거나 탈락 문항·복사 문항을 끼워 넣지 않는다. 임시 통과 문항은 DB에 저장하거나 사용자에게 풀도록 제시하지 않는다.

적합한 근거가 한 개뿐이어도 서로 다른 유효 문항을 만들 수 있으면 재사용할 수 있다. 근거가 있다는 이유만으로 어떤 문항 수도 만들 수 있다고 가정하지 않는다. 다른 문항을 확보하지 못하면 실패한다. 후보가 전혀 없으면 생성 전에 400으로 종료한다.

보충 루프는 부모 그래프가 관리한다. 라운드·슬롯별 고유 키로 병렬 결과를 합치고, 통과 문항·부족 개수·중복 이력·탈락 사유·라운드 수를 요청 상태에 둔다. 분기 내부 시도 횟수와 부모 라운드 수를 분리한다. 동시 모델 호출 상한은 기존 5개를 유지한다.

### 4. 종료 예산·오류·진행 안내

권장 초기 예산: 첫 라운드를 포함해 최대 5라운드, 각 슬롯의 라운드당 모델 생성 최대 2회, 요청 전체 120초. 문항 수 N일 때 업무 생성 호출 상한은 10N회이며, 어댑터의 기존 통신 재시도는 별도로 제한된다. 요청 deadline과 라운드 상한 중 먼저 도달한 조건으로 끝낸다. 남은 시간이 부족하면 새 모델 호출을 시작하지 않는다. 실제 지연과 비용을 측정해 조정한다.

| 조건 | API 결과 | 사용자 안내·저장 |
| --- | --- | --- |
| 처리 완료된 출제 근거 없음 | 400 | 자료 업로드·처리 상태 확인. 저장 없음 |
| 잘못된 문항 수·난이도 | 422 | 입력 수정. 모델 호출·저장 없음 |
| 같은 워크스페이스 생성 중 | 409 | 완료 후 재시도. 기존 요청 유지 |
| 검증·중복 실패로 라운드 소진 | 422 | ‘요청한 N문항을 모두 만들지 못했어요. 다시 시도하거나 자료를 추가해 주세요.’ 저장 없음 |
| 요청 시간 초과 | 503 | 시간 초과와 재시도 안내. 저장 없음 |
| 모델 공급자 사용 불가 | 503 | 일시적 장애 안내. 저장 없음 |
| 정확히 N문항 확보 | 201 | 완성 퀴즈 저장·표시 |

일부 분기에만 공급자 장애가 나면 사용 가능한 나머지 분기와 보충 예산으로 채운다. 공급자 장애로 전체 요청을 더 진행할 수 없으면 503으로 종료한다. 검증 실패·공급자 장애·시간 초과가 섞이면 deadline 도달을 먼저 판정하고, 다음으로 전체 진행 불가 여부를 판정하며, 나머지 개수 부족은 422로 처리한다. 어떤 종료 경로에서도 생성 잠금을 해제한다.

동기 생성 API를 유지한다. 화면은 경과 시간과 ‘선택한 문항을 생성·검증하고 있어요. 부족한 문항은 다시 만들어요’를 표시한다. 실시간 서버 진행률이 없으므로 확정된 통과 개수나 라운드 수를 화면에서 추측하지 않는다. 기존 ‘길어도 45초’ 문구는 새 예산에 맞춰 수정하고 프런트·개발 프록시의 요청 제한도 점검한다.

### 5. API·저장·이전 데이터

- 기존 퀴즈 생성 POST 요청에 count와 difficulty를 받는다. 생략 시 5·medium을 적용하여 기존 클라이언트 호출을 유지한다.
- 생성·제출 전 조회·제출 후 조회·목록 응답에 difficulty를 추가한다. requested_count·actual_count는 유지하되 신규 생성 성공에서는 항상 같다.
- 퀴즈 레코드에 난이도를 저장한다. 기존 퀴즈는 난이도를 알 수 없으므로 ‘미지정’으로 표시한다. 이전 문항에 임의로 ‘보통’을 부여하지 않는다. 이전 부분 퀴즈의 실제 문항 수·점수도 변경하지 않는다.
- 퀴즈와 전체 문항은 기존처럼 한 트랜잭션에 저장한다. 부분 결과·실패 결과·빈 퀴즈는 저장하지 않는다. 기존 제출 1회 확정과 오답 중복 방지를 유지한다.
- API·브라우저 목 모드도 같은 설정과 완료 조건을 따른다. 기존 부분 생성 성공 시나리오는 ‘초기 탈락 후 보충 성공’과 ‘보충 소진 후 전체 실패’로 바꾼다. 기존 부분 퀴즈 조회 시나리오는 호환성 검증에 남긴다.
- Langfuse에는 요청 문항 수·난이도·프롬프트 버전, 라운드별 통과·탈락·중복·부족 개수, 근거 교체, 호출 수·지연·종료 사유를 남긴다. 실패 시에도 확보 개수를 진단용으로 기록하되 성공 결과로 노출하지 않는다.

### 6. 정답·해설의 참고 자료

각 채점 문항은 선택지·정답 표시 → 해설 → 참고 자료 순서로 표시한다. 참고 자료에는 자료명, 1부터 시작하는 페이지, 원문 인용문, 원문 열기 동작을 함께 둔다. 예: ‘참고 자료 · Transformer 자료.pdf · 3페이지’. 긴 자료명은 화면을 깨뜨리지 않고 전체 이름을 확인할 수 있게 한다.

- 기존 document_id·filename·page·quote와 PDF 열람 패널을 재사용한다. 서버가 실제 근거 청크에서 채운 정보만 쓰며 모델이 자료명·페이지·인용문을 만들어내지 못하게 한다.
- 새 문항은 유효한 자료·페이지·청크 관계와 비어 있지 않은 근거 인용문을 확보해야 통과한다. quote는 기존의 연속 1~3줄·최대 160자 추출 정책을 따른다.
- 제출 전에는 기존 문항 출제 위치 표시를 유지할 수 있으나 정답·해설·quote를 API와 화면 모두에서 노출하지 않는다.
- 참고 자료를 누르면 해당 자료의 정확한 페이지를 기존 패널에서 연다. 가능한 경우 기존 인용문 하이라이트를 재사용한다. 패널을 닫아도 결과·풀이 상태를 유지한다.
- 맞힌 문항·틀린 문항·오답 상세에 동일한 참고 자료 표시를 제공한다. 관련 노트는 기존 기능으로 유지하되 실제 출제 근거인 자료와 구분한다.
- 기존 문항의 quote가 비어 있으면 ‘저장된 인용문 없음’을 표시하고 유효한 자료명·페이지 이동은 제공한다. 자료가 열람 불가하면 ‘원문을 열 수 없음’을 표시하고 이동을 비활성화하되 저장된 해설·인용문은 유지한다. 자료명이 없으면 ‘자료명 확인 불가’로 표시한다.
- 현재 문항당 실제 출제 근거는 하나다. 이번 변경은 이를 명확히 표시하는 범위이며 여러 자료를 종합한 문항과 복수 근거 저장 구조는 추가하지 않는다.

## Testing Decisions

사용자 확인: 자동 테스트는 **생성·검증 모듈과 API·저장 모듈**에 집중한다. 화면은 실제 렌더링·상호작용으로 수동 검증한다. 기존 퀴즈 그래프 테스트와 3일차 API·이전 DB 마이그레이션 테스트의 임시 DB, 모델 대역, 고정 난수 방식을 확장한다.

좋은 테스트는 반환 문항 수·근거 범위·설정 전달·응답 필드·저장 결과·실패 계약을 관찰한다. 그래프 노드명·호출 순서·내부 구현을 그대로 복제하지 않는다. 시간 초과는 제어 가능한 시계·대역으로 재현하며 실제 시간을 기다리지 않는다.

| 인수 기준 | 검증 |
| --- | --- |
| AC01. 1~10의 선택값과 난이도가 최초·보충 생성까지 전달된다 | 경계값 1·10, 세 난이도, 기본값, 잘못된 값의 API 테스트. 실패 입력은 모델 호출·DB 쓰기 없음 |
| AC02. N문항 요청의 신규 성공은 정확히 N문항이다 | 근거가 충분한 정상 생성과 후보 청크 수가 N보다 적은 상황 모두 확인 |
| AC03. 최초 5개 중 2개 탈락 후 보충 성공 시 유효한 5개가 저장된다 | 기존 통과 3개 보존, 부족분 보충, requested_count·actual_count·DB·응답 개수 일치 |
| AC04. 중복 문항은 개수에 포함하지 않고 대체 생성한다 | 공백·대소문자·선택지 순서만 다른 동일 문항, 근거 재사용 중복, 최종 고유 문항 수 확인 |
| AC05. 최초 전부 탈락해도 예산 안에서 보충에 성공하면 정상 완료된다 | 초기 탈락만으로 즉시 0문항 실패 처리하지 않음 |
| AC06. 부족분을 끝내 채우지 못하면 부분 퀴즈를 남기지 않는다 | 일부 통과 상태의 라운드 소진 422·deadline 503, quizzes·questions 쓰기 없음, 잠금 해제 |
| AC07. 공급자 장애와 동시 요청은 기존 계약을 지킨다 | 전체 장애 503, 일부 장애 후 보충 성공, 혼합 종료 우선순위, 동일 워크스페이스 409, 다른 워크스페이스 영향 없음 |
| AC08. 근거 범위를 벗어난 문항은 저장되지 않는다 | 다른 워크스페이스·미처리 자료 제외, 잘못된 페이지·청크 관계 및 빈 인용문 거절 |
| AC09. 정답을 공개하는 시점을 지킨다 | 생성·미제출 조회에는 정답·해설·quote 없음. 제출·제출 후 조회에는 정확한 근거 필드와 함께 존재 |
| AC10. 설정과 기존 기록이 재시작 후 유지된다 | 신규 난이도 저장·조회·목록 일치, 이전 DB 마이그레이션·미지정 표시용 값, 이전 부분 퀴즈 조회·채점 보존 |
| AC11. 선택지 섞기와 채점·오답이 일관된다 | 섞은 후에도 정답 텍스트 일치, 제출 1회·재제출 불변·오답 중복 방지 회귀 검증 |
| AC12. 해설에서 원문으로 돌아갈 수 있다 | 실제 화면에서 맞힌 문항·틀린 문항·오답 상세의 자료명·페이지·quote와 정확한 PDF 페이지 이동 확인 |
| AC13. 긴 자료명·누락 인용문·열람 불가 자료도 이해 가능하다 | 좁은 화면과 키보드 이동을 포함한 수동 검증. 기존 해설·학습 기록 유지 |
| AC14. 화면·목 모드가 실제 계약과 일치한다 | 두 생성 진입점, 설정 잠금·유지, 보충 성공·전체 실패, 과거 부분 퀴즈와 난이도 미지정 표시 수동 검증 |

실제 모델 검증은 두 데모 자료로 난이도별 5문항씩 총 15문항을 생성해 사람이 정답 유일성·근거 일치·난이도 설명 부합 여부를 판정한다. 정답·해설 오류나 근거 밖 지식 의존은 출시 전 수정한다. 이 검토는 자동 형식 검증과 별개다. 1·5·10문항 요청의 지연·호출 수·보충 횟수도 측정하고, 120초·5라운드 기본안의 적절성을 기록한다. 아직 실행하거나 통과한 검증은 아니다.

## Out of Scope

- 주관식, 문항별 혼합 난이도, 적응형 난이도와 학습자 수준 추정.
- 노트에서 출제, 외부 웹 검색, 여러 자료를 종합한 문항·복수 근거 스키마.
- 문항을 하나씩 스트리밍, 비동기 작업 큐, 서버 실시간 진행률, 실패 요청의 임시 문항 복구.
- 무한 재시도, 검증 기준 완화, 중복 문제로 개수 채우기.
- 기존 퀴즈의 재생성·문항 수정·난이도 추정, 기존 부분 퀴즈 삭제.
- 프런트 전체 개편과 화면 자동 테스트 체계 신설.

## Further Notes

- 확정된 요구: 문항 수·난이도 선택, 탈락 문항 자동 보충, 요청 수를 채운 경우에만 신규 성공, 정답·해설의 참고 자료 표시. 사용자가 확인한 범위는 위 세 모듈과 생성·API 중심 자동 테스트다.
- 권장 기본안: 1~10문항·기본 5, 세 난이도·기본 보통, 5라운드·120초. 구현 시 실제 GMS 지연·비용·문항 품질을 확인하고 조정하며 확정값을 관련 문서에 함께 반영한다.
- 구현 순서: 설정·저장 계약 확장 → 완성 개수 불변 조건과 보충 그래프 → 설정 화면·목 모드 → 해설·오답 참고 자료 → 회귀 및 실제 모델 검증. 구현·검증 결과는 기존 퀴즈 구현 기록에 덧붙인다.
- 문서 확인 시 제품 저장소에 Git 원격 설정이 없고 지정된 이슈 트래커 주소도 없었다. PRD는 이 문서를 최신본으로 보관한다. 이슈 게시와 ready-for-agent 라벨 적용은 수행하지 않았다. Notion은 수정하지 않는다.
