# StudyLink 2일차 PRD — 워크스페이스의 여러 채팅과 공통 학습 자원

작성일: 2026-10-21 (Asia/Seoul)  
상태: 구현용 요구사항. 채팅·공통 자원·노트 CRUD/연결/색인·채팅 문맥·재검색은 구현되었다([2일차 통합 기록](day2-integration.md)). 노트 초안·관련 노트·평가 도구는 미구현이다.  
사용자 확인: 워크스페이스 안에 여러 채팅을 두고 각 채팅의 문맥을 유지한다. PDF·연결 노트는 워크스페이스의 모든 채팅에서 열람·검색한다. 퀴즈 생성 준비는 3일차로 이동한다. 이슈 트래커는 아직 없으므로 로컬 문서로 관리한다.  
기준: [구현기획서 v1.1](studylink-implementation-plan-v1.1.md), [아키텍처](studylink-architecture.md), [1일차 통합 기록](day1-integration.md), [용어집](../CONTEXT.md), [ADR 0001](adr/0001-langgraph-without-langchain.md).

## Problem Statement

학습자는 같은 과목의 자료를 공유하면서 여러 주제를 별도 채팅으로 공부하고 싶다. 워크스페이스마다 질문 화면 하나만 있으면 대화가 섞이고, 채팅마다 PDF를 다시 올리게 하면 자료 관리가 중복된다. 각 채팅에서는 “그 내용을 더 설명해 줘”와 같은 후속 질문도 이어갈 수 있어야 한다.

학습자는 PDF 자료에서 얻은 답변을 자기 말로 정리하고, 다른 과목을 공부할 때 다시 활용하고 싶다. 현재 구현은 PDF 업로드와 근거 답변까지 제공하지만, 답변을 노트로 저장하거나 다른 워크스페이스의 검색 범위에 연결할 수 없다. 답변을 따로 복사하면 원문 페이지와의 관계가 끊어지고, 워크스페이스마다 복사본을 만들면 수정 내용도 서로 달라진다.

또한 답변 인용에서 화면 안의 PDF 페이지로 이동하고, 저장된 답변을 다시 여는 흐름이 필요하다. 검색된 근거가 약할 때는 한 번 더 검색하되, 관련 없는 노트를 억지로 근거에 넣거나 외부 서비스 장애를 근거 부족으로 표시해서는 안 된다.

## Solution

**2일차 완료 흐름은 워크스페이스에서 채팅 생성·전환 → 공통 PDF·연결 노트 열람 → 채팅 문맥을 이어가는 근거 답변 → 노트 초안·저장 → 다른 채팅 또는 연결된 다른 워크스페이스에서 노트 활용이다.**

답변을 요약한 노트 초안을 만들고, 사용자가 제목·본문·인용을 확인한 뒤 저장한다. 노트 원본은 하나만 유지하며 여러 워크스페이스에 연결한다. 답변은 현재 워크스페이스의 자료와 연결 노트만 검색하고, 자료 인용은 PDF 페이지로, 노트 인용은 노트 미리보기로 이어진다. 저장하지 않은 노트 초안은 검색되지 않는다.

노트 저장과 검색 색인의 성공 여부를 구분한다. 임베딩이 실패해도 사용자가 작성한 내용은 보존하고 재저장을 안내한다. 노트 초안 생성이 실패하면 원 답변을 옮긴 초안으로 이어서 편집할 수 있다.

## User Stories

1. 학습자로서, 답변의 자료 인용을 눌러 화면 안에서 해당 PDF 페이지를 열고 싶다. 설명과 원문을 바로 대조하기 위해서다.
2. 학습자로서, 같은 PDF의 다른 페이지 인용도 정확히 열고 싶다. 이전 페이지에 머물러 잘못 확인하지 않기 위해서다.
3. 학습자로서, 워크스페이스의 최근 답변을 다시 열고 싶다. 새로고침 후에도 학습을 이어가기 위해서다.
4. 학습자로서, 근거 답변에서 노트 초안을 만들고 싶다. 핵심 내용을 직접 다시 옮기는 수고를 줄이기 위해서다.
5. 학습자로서, 초안의 제목과 Markdown 본문을 수정하고 싶다. 내 이해에 맞게 정리하기 위해서다.
6. 학습자로서, 초안에 원 답변에서 확인한 인용만 남기고 싶다. 새로 만들어진 출처를 믿지 않기 위해서다.
7. 학습자로서, 요약 서비스가 실패해도 원 답변을 옮긴 초안을 받고 싶다. 노트 작성을 계속하기 위해서다.
8. 학습자로서, 요약 없이 답변을 옮긴 경우 안내받고 싶다. 초안을 검토할 때 생성 방식을 알기 위해서다.
9. 학습자로서, 근거 부족 답변에서는 초안 생성이 제한되길 원한다. 확인되지 않은 설명을 노트로 옮기지 않기 위해서다.
10. 학습자로서, 저장 전 초안이 질문 검색에 나오지 않길 원한다. 검토를 마친 노트만 활용하기 위해서다.
11. 학습자로서, 답변 없이 직접 노트를 작성하고 싶다. 내가 정리한 지식도 저장하기 위해서다.
12. 학습자로서, 제목·본문·노트 인용을 함께 저장하고 싶다. 다시 열어도 근거를 확인하기 위해서다.
13. 학습자로서, 노트 본문에서 지운 인용이 저장 결과에서도 빠지길 원한다. 사용하지 않는 근거가 남지 않기 위해서다.
14. 학습자로서, 대응하는 원본 정보가 없는 인용 표시는 저장 전에 안내받고 싶다. 깨진 인용을 수정하기 위해서다.
15. 학습자로서, 전체 노트 목록과 제목 검색을 사용하고 싶다. 다른 워크스페이스에서 작성한 노트도 찾기 위해서다.
16. 학습자로서, 노트를 특정 워크스페이스에 연결하지 않고도 저장하고 싶다. 나중에 활용할 정리를 보관하기 위해서다.
17. 학습자로서, 노트 하나를 여러 워크스페이스에 연결하고 싶다. 과목을 넘나들며 같은 지식을 활용하기 위해서다.
18. 학습자로서, 노트를 수정하면 연결된 모든 워크스페이스에서 수정 내용을 활용하고 싶다. 복사본을 따로 관리하지 않기 위해서다.
19. 학습자로서, 한 워크스페이스에서 연결을 해제해도 노트 원본과 다른 연결은 유지되길 원한다. 검색 범위만 조정하기 위해서다.
20. 학습자로서, 이미 연결한 노트를 다시 선택해도 중복 연결되지 않길 원한다. 목록과 검색 결과가 중복되지 않기 위해서다.
21. 학습자로서, 질문할 때 연결 노트 포함 여부를 선택하고 싶다. 자료만 확인하거나 내 정리를 함께 활용하기 위해서다.
22. 학습자로서, 다른 워크스페이스에만 연결된 노트는 질문에 섞이지 않길 원한다. 선택한 학습 범위를 유지하기 위해서다.
23. 학습자로서, PDF가 없고 연결 노트만 있는 워크스페이스에서도 질문하고 싶다. 기존 정리만으로 복습하기 위해서다.
24. 학습자로서, 답변에서 자료와 내 노트 인용을 구분하고 싶다. 근거의 성격을 파악하기 위해서다.
25. 학습자로서, 노트 인용을 눌러 해당 노트를 미리 보고 싶다. 답변이 참조한 정리를 확인하기 위해서다.
26. 학습자로서, 연결 노트가 질문과 관련 있을 때 근거 후보에 포함되길 원한다. 긴 PDF 청크에 내 정리가 밀리지 않기 위해서다.
27. 학습자로서, 관련 없는 노트는 연결되어 있어도 근거로 쓰이지 않길 원한다. 질문과 무관한 설명을 피하기 위해서다.
28. 학습자로서, 노트 검색 색인이 실패해도 저장한 본문은 보존되길 원한다. 작성 내용을 잃지 않기 위해서다.
29. 학습자로서, 색인 실패 상태와 재저장 안내를 보고 싶다. 노트가 검색되지 않는 이유와 복구 방법을 알기 위해서다.
30. 학습자로서, 수정한 노트의 색인이 실패하면 예전 본문이 검색되지 않길 원한다. 현재 노트와 다른 설명을 답변에서 보지 않기 위해서다.
31. 학습자로서, 편집 중 버튼을 눌러 관련 노트 최대 3개를 보고 싶다. 저장 전에 기존 정리와 비교하기 위해서다.
32. 학습자로서, 관련 노트 제안에서 편집 중인 노트와 중복 항목이 빠지길 원한다. 다른 노트를 쉽게 찾기 위해서다.
33. 학습자로서, 처음 검색한 근거가 약하면 한 번 더 검색하길 원한다. 질문 표현 차이 때문에 답을 놓치지 않기 위해서다.
34. 학습자로서, 재검색 후에도 근거가 부족하면 보류 안내를 받고 싶다. 확인되지 않은 답을 학습하지 않기 위해서다.
35. 학습자로서, 초안 생성·저장 중 진행 상태와 실패 안내를 보고 싶다. 중복 요청을 피하고 입력 내용을 유지하기 위해서다.
36. 학습자로서, 앱을 재시작해도 노트·인용·연결과 저장된 답변을 열고 싶다. 학습 결과를 계속 활용하기 위해서다.
37. 개발 팀원으로서, 검색 범위·노트 보장·재검색·초안 fallback을 목 모드에서 재현하고 싶다. 외부 서비스 없이 실패 경로를 검증하기 위해서다.
38. 개발 팀원으로서, 평가 질문별 근거와 인용·보류 결과를 기록하고 싶다. 검색 기준값을 근거 있게 조정하기 위해서다.
39. 학습자로서, 워크스페이스 안에 여러 채팅을 만들고 싶다. 같은 과목의 서로 다른 주제를 나누어 공부하기 위해서다.
40. 학습자로서, 채팅을 전환하면 그 채팅의 질문·답변 기록만 보고 싶다. 다른 주제와 혼동하지 않기 위해서다.
41. 학습자로서, 같은 채팅에서 이전 질문·답변을 이어 묻고 싶다. 매번 주제를 다시 설명하지 않기 위해서다.
42. 학습자로서, 새 채팅에는 다른 채팅의 문맥이 섞이지 않길 원한다. 독립적으로 새 주제를 시작하기 위해서다.
43. 학습자로서, 모든 채팅에서 워크스페이스의 PDF와 연결 노트를 열고 싶다. 같은 자료를 반복 업로드하거나 복사하지 않기 위해서다.
44. 학습자로서, 답변 인용을 누르지 않아도 공통 자원 목록에서 원문과 노트를 열고 싶다. 질문 전후에 자료를 직접 읽기 위해서다.
45. 학습자로서, 한 채팅에서 저장해 워크스페이스에 연결한 노트를 다른 채팅에서도 활용하고 싶다. 검토한 지식을 대화 사이에서 재사용하기 위해서다.
46. 학습자로서, 재시작·새로고침 후에도 채팅 목록과 선택한 채팅의 기록을 복구하고 싶다. 이어서 공부하기 위해서다.
47. 학습자로서, 기존에 저장한 질문·답변도 이전 대화에서 열고 싶다. 채팅 구조 변경으로 학습 기록을 잃지 않기 위해서다.

## Implementation Decisions

### 확인된 출발점

- 1일차 제품 저장소에는 PDF 수집·자료 검색·답변 저장·인용 검증·출력 재생성 최대 1회가 구현되어 있다. 노트 관련 테이블도 준비되어 있다. 이를 새로 만드는 일정으로 잡지 않는다.
- 현재 검색 구현은 자료만 조회한다. 연결 노트 검색, 노트 1개 보장, 실제 질의 재작성·재검색은 추가해야 한다.
- 현재 HTTP 라우터에는 노트·연결·초안·최근 답변 조회 API가 없다. 답변 저장 구현과 조회 화면 완료를 구분한다.
- 1일차 통합 기록의 자동 테스트 22개 통과와 실제 GMS 확인은 이전 검증 결과다. 이번 PRD 작성 중 제품 테스트를 다시 실행하거나 2일차 기능을 검증한 것은 아니다.

### 모듈 경계와 담당

2026-10-21 추가 요구는 [ADR 0002](adr/0002-workspace-chats-shared-resources.md)를 따른다. 채팅 저장·조회·이관은 B, 채팅 목록·전환·기록·공통 자원 패널은 A, 채팅 문맥 해석·근거 검색·생성은 C가 맡는다.

| 모듈 | 외부 계약 | 내부에 묶는 책임 | 담당 |
| --- | --- | --- | --- |
| 학습·노트 화면과 API 클라이언트 | 답변 복구, 인용 열기, 초안·노트 편집, 연결 선택 | 요청 상태, 입력 유지, PDF 재마운트, 인용 종류별 표시 | A |
| 노트 저장·색인 서비스 | 노트 생성·조회·수정, `index_note(note_id)` | 인용 검증, 연결 저장, 청킹·임베딩 교체, 실패 시 내용 보존 | B, C 임베딩 계약 지원 |
| 노트 연결 서비스 | 연결·해제·워크스페이스별 목록 | 중복 방지, 원본 유지, 검색 범위 반영 | B |
| 근거 검색 도구 | `retrieve(workspace_id, query, include_notes)` | 범위 필터, 모델·차원 검사, 관련성 선택, 노트 보장, 상한 | C |
| 답변 그래프·서비스 | `answer_question(...)`, 최근·단건 답변 조회 | 제한된 재검색·재생성, 인용 검증, 결과 저장·복구 | C 그래프, B 조회 API |
| 노트 초안 그래프·서비스 | `draft_note(answer_id)` | 원 답변 조회, 요약·검증·재생성, 인용 재번호화, fallback | C 그래프, B HTTP 연결 |
| 관련 노트 검색 | `related_notes(text, exclude_note_id, k=3)` | 전체 노트 검색, 노트별 중복 제거, 자기 자신 제외 | C 검색, B HTTP 연결 |
| 평가 도구 | 질문셋 입력 → 판정용 결과 | 기대 인용·보류 비교, 근거·재검색·trace 기록 | C |

인용 정규화·색인 교체·검색 범위와 실패 복구는 위 서비스의 단순한 계약 뒤에 감춘다. 작은 내부 단계마다 별도 서비스나 그래프를 추가하지 않는다. 기존 React·FastAPI·SQLite·LangGraph·GMS 어댑터 구성을 유지한다.

### HTTP 계약

채팅을 사용하는 화면의 기본 계약은 `GET/POST /api/workspaces/{id}/chats`, `GET /api/chats/{id}`, `GET /api/chats/{id}/messages`, `POST /api/chats/{id}/ask`다. messages는 완료된 질문·답변 쌍을 시간순으로 반환하고 각 항목에 question과 기존 답변 필드를 포함한다. 채팅은 id, workspace_id, title, created_at, updated_at을 가진다. 기존 워크스페이스 ask는 호환용으로 기본 채팅에 연결하며 새 화면은 채팅별 ask를 사용한다.

| 기능 | 계약과 기대 동작 |
| --- | --- |
| 답변 복구 | `GET /api/workspaces/{id}/answers` 최근 20개, `GET /api/answers/{id}`는 질문 응답과 같은 형식 |
| 노트 초안 | `POST /api/answers/{id}/note-draft` → title, body, citations, fallback. DB 저장 없음 |
| 노트 목록 | `GET /api/notes`의 q는 제목 검색, workspace_id는 연결 범위 필터 |
| 노트 생성 | `POST /api/notes`에 title, body, workspace_ids, citations 전달 |
| 노트 조회·수정 | `GET/PUT /api/notes/{id}`. 저장·조회 응답에 index_status 포함 |
| 연결·해제 | `POST/DELETE /api/workspaces/{id}/notes/{note_id}`. 해제는 원본 삭제가 아님 |
| 관련 노트 | `POST /api/notes/related`에 title, body, 선택적 exclude_note_id → note_id, title, snippet 최대 3개 |
| 질문 | 기존 ask의 include_notes를 실제 검색에 반영하고 doc/note 인용 계약 유지 |

워크스페이스 상세에는 연결 노트 목록을 포함한다. 없는 답변·노트·워크스페이스는 404, 유효하지 않은 입력·인용은 422이며 기존 detail 오류 형식을 유지한다. 노트 삭제 API는 이번 범위에 추가하지 않는다.

### 노트 원본·인용·색인

- 노트는 워크스페이스에 소유되지 않는다. 연결 관계로만 검색 범위에 포함하며, 연결·해제만으로 재임베딩하지 않는다.
- 요청 단위 근거 번호 `[eN]`은 초안에서 영속 노트 인용 `[cN]`으로 바꾼다. 자료는 자료 ID·1부터 시작하는 페이지·발췌, 노트는 인용 대상 노트 ID를 서버에서 매핑한다.
- 저장 시 본문에 남은 `[cN]`에 대응하는 인용만 보관한다. 본문에 대응 정보 없는 표시가 있으면 422로 거절한다. 인용 번호는 노트 안에서 고유하다.
- 원본 노트 제목은 조회 시 현재 값을 사용한다. 인용 대상 노트가 없어지면 인용 관계는 보존하고 missing 표시로 안내하는 기존 계약을 유지한다.
- 노트 청크는 제목과 본문 문단으로 만든다. 수정 시 예전 청크를 교체하고, 임베딩 실패 시 새 본문·인용은 저장하되 예전 청크를 제거하고 index_status=failed로 검색에서 제외한다. 다음 저장 성공 시 ok로 복구한다.
- 외부 임베딩 호출 동안 SQLite 쓰기 트랜잭션을 유지하지 않는다. 저장된 본문과 다른 청크가 검색되지 않도록 교체 경계를 서비스 안에서 관리한다. 목·실제 DB 및 임베딩 모델·차원 격리를 유지한다.

### 검색·재검색

- 채팅의 workspace_id를 서버에서 조회하여 검색 범위를 정한다. 다른 채팅의 기록은 문맥에 포함하지 않는다. 최근 완료 대화 최대 6쌍·문맥 최대 12,000자를 사용하고, 기록 조회와 모델에 제공하는 문맥 길이를 구분한다.
- 후속 질문은 해당 채팅 문맥을 참고해 독립적인 검색 질의로 해석한다. 이 해석과 약한 근거 재검색은 구분하며 모두 기존 30초 요청 예산 안에서 실행한다. 과거 답변·인용 번호를 새로운 사실 근거나 이번 요청의 근거 ID로 재사용하지 않는다.
- 동일 채팅의 답변 생성 중 추가 요청은 409로 안내하여 순서 뒤섞임을 막는다. 다른 채팅은 각각 독립된 상태를 사용한다.

- 검색 전에 현재 워크스페이스의 ready 자료와, include_notes가 참이면 연결된 색인 성공 노트만 후보로 제한한다. 노트만 있는 워크스페이스도 질문할 수 있다.
- 범위 내 검색 가능한 후보가 아예 없으면 기존 400 안내를 유지한다. 후보는 있지만 최소 점수를 넘는 근거가 없을 때 질의 재작성·재검색을 최대 1회 수행한다. 재검색 후에도 근거가 없으면 insufficient_evidence다.
- 재작성은 검색 질의 문자열만 바꾼다. 워크스페이스·include_notes는 유지하고 생성에는 원 질문을 사용한다. 두 검색 결과는 chunk_id로 합치고 중복은 높은 점수를 택한 뒤 선택 규칙을 다시 적용한다.
- 최소 점수 → 최고 점수 대비 상대 기준 → 최대 12개·약 8,000자 상한을 유지한다. 최소 점수를 넘은 노트가 있는데 결과에 없다면 최고 점수 노트 1개를 넣고, 필요하면 마지막 자료 근거를 빼서 상한을 지킨다.
- 노트 보장은 검색 근거 포함 규칙이다. 모델이 모든 질문에서 노트를 반드시 인용한다는 보장이 아니므로, 데모 질문에서 실제 노트 인용까지 별도로 확인한다.
- 기존 출력 재생성 최대 1회와 무효 인용 제거를 유지한다. 공급자 장애는 503이며 근거 부족으로 바꾸지 않는다. 질의응답 30초 요청 예산을 재검색까지 공유한다. 현재 협력적 deadline 검사라는 제한도 유지한다.

### 노트 초안·관련 노트·화면

- 저장된 grounded 답변을 요약하고 원 답변 인용 범위로 검증한다. 출력 검증 실패는 최대 1회 재생성, 최종 실패·공급자 장애·20초 예산 소진 시 원 답변의 유효 문장을 문단으로 옮기는 결정적 fallback을 반환한다.
- insufficient_evidence는 초안 버튼을 비활성화하고 서버도 422로 거절한다. fallback=true는 “요약 없이 답변을 옮겨 담음”으로 표시한다. 초안은 저장 버튼을 눌러야 노트가 된다.
- 관련 노트는 버튼을 누를 때만 저장 전 제목·본문으로 전체 색인 성공 노트를 검색한다. 노트별 최고 점수 청크 하나를 택하고 편집 중 노트를 제외한다. 점수는 화면에 노출하지 않으며 검색 때문에 본문을 저장하지 않는다.
- 자료 인용 클릭 시 PDF 패널을 해당 자료·페이지로 갱신한다. 같은 자료의 페이지 변경도 반영되도록 뷰어를 다시 마운트한다. 노트 인용은 미리보기로 열고 자료와 내 노트 배지를 구분한다.
- 저장된 답변은 최근 목록·단건 조회로 복구한다. 저장하지 않은 초안의 새로고침 복구·자동 저장은 범위에 넣지 않는다.
- ask에는 선택 근거·점수·노트 보장·재검색 여부를, note_draft에는 원 답변 식별자·검증·fallback을 기록한다. 관측 장애는 업무 흐름을 막지 않는다. 기존 허용된 데모 자료와 비밀값 미기록 원칙을 유지한다.

## Testing Decisions

좋은 테스트는 공개 API·서비스 결과와 저장 후 조회 결과를 검증한다. SQL 문자열이나 내부 노드 호출 순서를 그대로 복제하지 않는다. 자동 테스트는 아래 범위를 제안하며 화면은 수동 통합 검증한다.

| 대상 | 검증할 외부 동작 |
| --- | --- |
| 노트 저장·인용 | 생성·수정·재조회, 혼합 인용 유지, 안 쓰는 인용 제거, 대응 정보 없는 표시 422, 거절된 저장의 부분 변경 없음 |
| 색인 | 성공 후 검색, 수정 내용 반영, 실패 시 본문 보존·예전 청크 미검색, 재저장 복구 |
| 연결 | 여러 워크스페이스에 같은 원본 연결, 중복 방지, 해제 후 원본·다른 연결 유지 |
| 검색 | 연결되지 않은 노트 제외, include_notes=false, 노트만 있는 범위, failed 색인·모델 불일치 제외, 최소 점수 미달 노트 미포함, 노트 보장과 개수·길이 상한 |
| 답변 그래프 | 약한 근거에서 재검색 후 성공/보류, 검색 범위 불변, 재검색 1회 종료, 기존 출력 재생성·인용 검증 유지, 공급자 오류 503 |
| 초안 | 원 답변 범위 인용과 재번호화, DB 미저장, 출력 재생성 소진·공급자 장애·deadline fallback, 근거 부족 422 |
| 관련 노트 | 최대 3개 고유 노트, 자기 자신 제외, 전체 노트 검색, 저장 전 내용 미영속화 |
| 조회·영속화 | 최근 답변 20개·단건 복구, 앱 재시작 후 노트·인용·연결 유지 |
| 채팅·문맥 | 같은 워크스페이스에서 여러 채팅 생성·전환, 공통 자원 열람·검색, 기록 격리, 후속 질문의 주제 해석, 다른 채팅 문맥 미사용, 이전 답변 이관 멱등성, 재시작 복구, 동일 채팅 중복 요청 409 |

기존 테스트의 선례는 임시 SQLite와 FastAPI TestClient를 사용하는 API 테스트, GMS 대역과 결정적 벡터를 사용하는 검색·답변 테스트, httpx 대역을 사용하는 어댑터 테스트다. 이 방식을 확장한다. 기존 “낮은 유사도에서 즉시 보류” 테스트는 새 재검색 계약에 맞춰 갱신한다. 외부 GMS·Langfuse 실측은 자동 테스트와 분리한다.

### 2일차 인수 시나리오

1. 워드 임베딩 자료에서 grounded 답변을 받고 p.3 인용을 화면 안에서 연다. 다른 페이지 인용으로 이동해 페이지 갱신도 확인한다.
2. 답변을 초안으로 만들고 제목·본문을 편집해 “기울기 소실 정리”로 저장한다. 재조회한 노트에서 본문·노트 인용이 유지되고 원문이 열려야 한다.
3. 동일 노트를 LLM 워크스페이스에 연결한다. Transformer 자료와 함께 “Residual connection은 왜 쓰는 거야?”에 질문해 자료 인용과 해당 노트 인용을 확인한다.
4. include_notes=false 및 연결 해제로 해당 노트가 검색 범위에서 빠지는지 확인한다. 다른 연결과 원본은 유지되어야 한다.
5. 노트만 연결한 워크스페이스에서 질문한다. 색인 성공 노트가 있으면 자료 없음 오류로 차단되지 않아야 한다.
6. 임베딩 실패를 주입해 수정 내용은 보존되고 과거 본문은 검색되지 않는지 확인한 뒤 재저장으로 복구한다.
7. 초안 생성 실패를 주입해 fallback 초안으로 저장까지 진행한다. 자료·노트 혼합 인용을 저장하고 다시 열어 두 원본 이동을 확인한다.
8. 서버 재시작·화면 새로고침 후 저장된 답변·노트·연결을 다시 열고 재질문한다.
9. 한 워크스페이스에 채팅 A·B를 만들고 두 채팅에서 같은 PDF·연결 노트를 연다. A의 질문·답변이 B의 기록에 나타나지 않아야 한다.
10. A에서 구체적 개념 질문 후 “그 내용을 더 설명해 줘”로 이어 묻는다. 같은 주제를 이해하고 현재 검색 근거를 인용해야 한다. B의 새 질문에는 A의 대화 문맥이 전달되지 않아야 한다.
11. 기존 답변이 있는 DB를 새 구조로 열어 이전 대화에 기록이 보존되는지, 다시 시작해도 중복되지 않는지 확인한다.

인수 항목은 실제 실행 후에만 완료로 표시한다. 실제 데모 자료로 핵심 흐름과 trace를 확인하고 목 테스트 통과와 구분해 기록한다.

### 검색 품질 보정

기존 데모 PDF 2개로 답 있음 10개·답 없음 5개의 평가 질문과 기대 페이지를 준비한다. 평가 도구는 근거 수·점수·노트 보장·재검색·답변 상태·인용·trace ID·자동 기대값 비교·사람 판정란을 기록한다. 2일차에는 이 결과로 최소 점수·상대 기준을 보정하고 사용한 설정과 실패 질문을 남긴다.

답 있음의 올바른 페이지 인용 8/10 이상, 답 없음 보류 4/5 이상은 기존 전체 시제품 목표다. 2일차 보정 결과를 측정 없이 통과로 표시하지 않는다. 인용 ID가 유효하다는 것과 실제 주장을 뒷받침한다는 것은 다르므로 후자는 사람이 판정한다. 전체 최종 판정은 3일차에 이어간다.

## Out of Scope

- 사용자 결정에 따라 퀴즈 생성 준비·생성 그래프·퀴즈 API·풀이·채점·오답 흐름은 모두 3일차로 이동한다.
- 로그인·다중 사용자, 공개 배포, Notion·삼성노트 연동, OCR·스캔 PDF, 사용자 간 공유.
- 노트 삭제 UI·정책, revision·버전 고정 인용, 자동 저장·미저장 초안 복구, 자동 관련 노트 갱신.
- PDF 문장 하이라이트, BM25 결합, 벡터 DB 교체, 무제한 재검색·도구 선택 에이전트.
- 전체 자료·노트 일괄 재색인 관리 스크립트는 별도 후속이다. 이번 노트 저장 시 재색인과 구분한다.

## Further Notes

### 일정과 우선순위

| 시점 | A 프런트 | B 백엔드 | C LangGraph·에이전트 |
| --- | --- | --- | --- |
| 2일 오전 | PDF 페이지 이동·답변 복구, 노트 API 목 계약 | 노트 저장·인용·색인·연결 API | 노트 검색·노트 보장·실제 재검색, 평가 질문·도구 착수 |
| 2일 오후 | 초안 편집·노트 저장소·연결 화면 | 초안·관련 노트 API, 저장 실패·복구 통합 | 초안 그래프·관련 노트 검색, 기준값 보정·trace 확인 |
| 2일 끝 | 노트 저장 → 다른 워크스페이스 연결 → 노트 인용 통합, 재시작·실패 흐름 확인(공동) | ← | ← |
| 3일차 인계 | 퀴즈·오답 화면 | 퀴즈 저장·조회·채점·오답 API | 퀴즈 생성 준비·그래프·검증, 최종 평가 |

퀴즈 준비 이동으로 3일차 부담이 늘어난다. 2일차 종료 시 핵심 통합이 실패하면 다음 날 오전에는 그 흐름을 먼저 복구한다. 기존 축소안대로 관련 노트 제안 C08을 먼저 제외할 수 있으나, 노트 연결 후 검색과 페이지 인용은 축소하지 않는다. 제외한 기능과 이유는 통합 기록에 명시한다.

### 문서와 게시 상태

- 이 PRD의 최신본은 제품 저장소의 docs에 둔다. 실습 저장소에는 최신본 링크만 남긴다.
- 이슈 트래커가 없다는 사용자 답변에 따라 외부 게시·ready-for-agent 라벨 적용은 수행하지 않았다. 트래커가 정해지면 이 문서를 근거로 게시한다.
- 퀴즈 준비 이동은 작업 순서 조정으로 기획서·아키텍처에 반영한다. 이후 추가된 채팅 소유권·공통 자원·문맥 격리 결정은 ADR 0002에 기록한다.
