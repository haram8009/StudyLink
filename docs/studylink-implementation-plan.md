## 1. 의사결정 요약

독립 웹서비스에서 PDF와 Notion 자료를 읽고 질문하며, 근거가 연결된 공부 노트를 작성·저장한다. 노트 원본을 여러 개인 워크스페이스에 연결하고, 새 노트를 쓸 때 허용된 이전 노트를 검색한다. 선택한 자료와 노트로 퀴즈를 만들고 오답에서 원문·관련 노트로 돌아가 복습한다.

권장 MVP는 개인 사용자 중심이다. 동일 사용자의 워크스페이스 간 노트 공유를 지원하고, 다른 사용자 초대·공개 공유는 후속으로 둔다. 삼성노트는 PDF·이미지 내보내기 파일을 가져오는 방식으로 지원한다. Notion은 선택 페이지 읽기와 수동 갱신부터 구현한다. 시맨틱 레이어·지식 그래프는 필수가 아니며, 관계형 데이터와 권한 필터가 적용된 의미 검색으로 시작한다.

핵심 가치 가설은 “새 학습 내용을 정리할 때 과거 노트와 원문을 다시 찾는 시간을 줄이고, 틀린 문제에서 필요한 자료로 쉽게 돌아간다”이다. 경쟁 서비스 대비 우위나 학습 성과 향상은 아직 입증되지 않았다.

## 2. 현재 저장소와 현실적인 출발점

확인한 작업 폴더는 D:/SSAFY/streamlit_lab이다. README.md는 Streamlit 실습과 3일 프로젝트 골격을 설명한다. step7_skeleton.py에는 가짜 문서 수집 함수, 대화 UI와 인용 번호를 표시하는 구조가 있다. 실제 RAG, 영속 DB, 문서 업로드 파이프라인, 사용자 인증은 구현된 것으로 확인되지 않았다. requirements.txt에는 Streamlit과 LangChain 계열 의존성이 있다. 현재 폴더는 Git 저장소로 인식되지 않는다.

기존 코드는 학습 자료로 보존하고 step7의 화면·근거 표시 패턴을 출발점으로 확장한다. 단기에는 Streamlit으로 학습 흐름을 검증한다. 제품 MVP에서는 편집·자동저장·PDF 위치 이동 요구를 고려해 React/TypeScript 프런트엔드와 Python API로 분리하는 것을 권장한다. Streamlit 계속 사용이 과제 조건이면 UI 교체를 미루고 동일한 도메인 서비스·저장소 계층을 재사용한다.

현재 GMS 호출 설정은 교육용 코드에서 확인했지만 사용 가능 모델·임베딩·외부 서비스 제공 허용 여부·요금은 확인하지 않았다. 운영 비용을 GMS 무료 사용 가정으로 산정하지 않는다.

## 3. 문제, 사용자, 성공 기준

### 사용자 문제

- 강의 PDF, Notion 필기, 삼성노트 필기가 흩어져 있다.
- 질문의 답을 받아도 어느 원문에 근거하는지 다시 확인하기 어렵다.
- 이전 과목의 개념을 새 노트에 연결하려면 직접 검색·복사해야 한다.
- 퀴즈 결과와 공부 노트가 분리돼 오답 복습이 반복 검색으로 끝난다.

### 대표 사용자와 목표

1. 전공 수업 학생: 강의 내용을 자신의 말로 정리하고 필요한 선수 개념을 찾는다.
2. 시험 준비 학생: 범위를 지정해 문제를 풀고 틀린 개념과 원문을 복습한다.
3. 논문을 읽는 학생·개발자: 같은 구조에서 논문도 자료로 넣는다. 코드 정확성 자동 검증은 범위 밖이다.

### 제품 지표와 검증 방식

- 핵심 완료율: 업로드 성공 사용자 중 “근거 답변 → 노트 저장 → 퀴즈 제출” 완료 비율. 파일럿 목표 60%.
- 연결 활용률: 관련 노트 제안 노출 중 열기·인용 추가 비율. 목표 20%, 단순 클릭보다 실제 노트 반영을 별도 측정.
- 자료 재탐색 시간: 10명의 동일 난이도 과제에서 기존 방식 대비 중앙값 30% 감소를 가설로 검증.
- 학습 효과는 정답률 상승만으로 주장하지 않는다. 반복 출제 효과와 원래 실력을 분리한 추가 실험이 필요하다.
- 기능 사용 이벤트만 집계하고 원문·개인 노트 본문을 분석 로그에 남기지 않는다.

## 6. 사용자 흐름과 화면 명세

### A. 첫 학습

로그인 → 과목 워크스페이스 생성 → 자료 업로드 → 처리 상태 확인 → 질문 → 근거 원문 열기 → 선택 답변을 노트 초안으로 보내기 → 편집·저장 → 범위 선택 퀴즈 → 제출·오답 저장.

자료가 없으면 업로드 안내를 제공한다. 처리 중 자료는 선택 불가로 표시하고 이미 준비된 자료로는 계속 질문할 수 있다. 실패 이유는 비밀번호 PDF, 손상 파일, 시간 초과, OCR 미지원 등 행동 가능한 메시지로 제공한다.

### B. 기존 지식 연결

노트 저장소에서 미적분 노트를 머신러닝 공간에 연결 → 경사하강법 노트 작성 → 관련 기록 조회 → 관련 문단과 연결 이유 확인 → 인용 삽입 또는 무시. 제안은 자동 본문 변경과 분리한다.

### C. 복습

오답 목록에서 항목 선택 → 당시 문제·자신의 답·해설 보기 → 근거 페이지/관련 노트 열기 → 틀린 이유 직접 기록 → 재풀이 또는 유사 문제 요청. 정답 처리 후에도 과거 오답 이력은 남는다.

| 화면 | 주요 영역 | 필수 상태 |
|---|---|---|
| 홈 | 워크스페이스, 최근 노트, 복습할 항목 | 첫 사용자·최근 활동 없음 |
| 워크스페이스 | 자료/대화/노트/퀴즈 탭, 검색 범위 선택 | 자료 처리 중·권한 소실 |
| 학습 화면 | 왼쪽 자료 목록, 중앙 원문, 오른쪽 질문·노트 전환 | 좁은 화면은 탭 전환 |
| 노트 편집 | 본문, 근거 패널, 관련 노트, 저장 상태 | 저장 중·충돌·색인 대기 |
| 저장소 | 제목·태그·연결 공간·수정일 필터 | 연결 해제와 삭제를 다른 메뉴로 |
| 퀴즈 | 범위/난이도/5·10문항, 문제, 제출 | 생성 실패·근거 불충분 |
| 오답노트 | 개념·과목·재풀이 상태 필터 | 원문 삭제·문제 무효 처리 |
| 연동/설정 | Notion 연결, 삭제, 사용량, 자료 처리 고지 | 토큰 만료·연결 해제 |

생성되는 문구·근거는 키보드로 탐색 가능하게 하고, 표·수식과 긴 인용에 모바일 가로 넘침 대책을 둔다. 데스크톱 우선이되 업로드·읽기·퀴즈는 휴대폰에서도 가능하게 한다. 펜 입력 편집기는 초기 제외다.

## 7. 저장·공유·검색의 의미

### 노트 원본과 연결

노트 소유자는 한 명이고 노트 ID는 전역적으로 하나다. workspace_notes가 여러 워크스페이스와 노트를 연결한다. A 공간에서 수정하면 B에서도 최신 원본을 본다. 복제는 명시적 “사본 만들기” 기능으로만 수행한다.

노트 연결은 해당 노트를 검색 대상으로 허용하는 의미다. 노트가 인용한 PDF 전체를 자동으로 연결하지 않는다. 본인 자료라도 현재 공간에 포함되지 않은 PDF는 “원문 보기”로 열 수 있되, 해당 PDF 전체 검색은 별도 자료 연결 후 수행한다. 인용된 문장 수준의 출처 확인과 전체 문서 검색 범위를 구별한다.

### 검색 범위

기본: 현재 워크스페이스의 준비된 자료 + 연결된 사용 확정 노트.
선택: “자료만”, “자료와 연결 노트”, “내 전체 저장소도 검색”.
전체 저장소 검색은 본인 소유만 허용하고 화면에 활성 범위를 계속 표시한다. 미저장 초안은 현재 요청의 문맥으로만 쓰며 다른 검색 결과에는 나타나지 않는다.

권한은 검색 전 필터, 원문 다운로드, 인용 조회, 답변 저장·노출 시점에 확인한다. 생성 중 자료가 삭제되거나 권한이 철회되면 결과를 보류한다. 사용자 간 공유가 생기기 전에도 owner_id를 모든 읽기 경로에서 강제한다.

### 삭제 규칙

- 연결 해제: 특정 공간의 검색에서 제외, 원본은 저장소에 유지.
- 보관: 기본 검색 제외, 사용자가 복원 가능.
- 삭제: 즉시 검색·원문 접근 차단. 비동기 파일·청크·벡터 제거 목표 24시간.
- 인용 대상 삭제: 기존 노트·답변에 “출처 삭제됨” 표시. 별도로 작성된 사용자 노트는 자동 삭제하지 않는다.
- 사용자 전체 계정 삭제: 노트·대화·문제·답안·토큰·파생 검색 데이터까지 삭제 작업.
- 백업 만료 기본 30일, 복원 시 삭제 목록을 재적용. 이는 제안 운영 정책이며 실제 인프라 설정과 맞춘다.

## 8. 문서 수집·OCR 파이프라인

권장 파서 후보는 Docling이다. 구조화 문서 표현을 보존할 수 있는지 실제 자료로 평가한다 [S5]. GROBID는 학술 메타데이터 특화가 필요할 때 후속 비교한다. 여러 파서를 동시에 운영하지 않고 20개 문서 평가 결과로 하나를 먼저 선택한다.

처리 단계:
1. MIME·크기·페이지 수·비밀번호·악성 파일 검사, 파일 해시 생성.
2. 사용자별 중복 확인. 같은 파일 재업로드는 기존 자료 연결 또는 새 버전 선택.
3. 격리된 워커에서 텍스트·레이아웃 추출.
4. 페이지별 텍스트 부족/깨짐을 판별하여 해당 페이지만 OCR 후보로 지정.
5. 원문 구조·제목 경로·표·수식·페이지 좌표를 정규화.
6. 검색 청크 생성 및 임베딩.
7. 모든 필수 단계 성공 후 active_version_id를 원자적으로 교체.
8. 페이지 수·누락·OCR 경고가 포함된 처리 결과 제공.

기본 제한 제안: 파일 30MB, PDF 200페이지, 사용자 총 1GB. 문자 PDF는 100페이지 이하부터 품질 검증. 초기 삼성노트 필기는 20페이지 이하 권장. 용량 제한은 압축된 크기뿐 아니라 렌더링 픽셀 수·메모리·처리 시간에도 적용한다.

상태: uploaded → queued → parsing → ocr_optional → indexing → ready. 분기: needs_review, failed, cancelled. 일부 페이지 실패는 ready_with_warnings로 표시하고, 검색에 사용한 범위를 알려준다. 실패한 새 버전이 이전 정상 버전을 대체하지 않는다.

한국어 손글씨·수식·화살표는 별도 평가군이다. 추출 불확실성을 정확한 확률처럼 보여주지 않는다. 의심 영역을 표시하고 원문과 대조·수정할 수 있게 한다. OCR 수정은 새 추출 버전으로 저장한다. 수식 인식 미지원이면 해당 영역은 이미지로 보존하고 자동 출제에서 제외한다.

좌표 계약: PDF 페이지 인덱스는 저장 시 0부터, UI는 1부터. 인쇄된 페이지 번호는 별도 page_label이다. bbox는 왼쪽 위 원점 기준 0~1 정규화 값으로 변환하고 회전값·원본 크기를 보관한다. 페이지를 가로지르는 청크는 복수 locator를 가진다. 좌표가 없으면 페이지와 인용문만 표시하며 가짜 하이라이트를 만들지 않는다.

## 9. RAG와 근거 검증

### 수집 단위

문단·제목·표를 보존해 400~800토큰 청크, 최대 100토큰 겹침을 초기 실험값으로 둔다. 표·수식은 가능한 한 분리하지 않고 캡션·제목 경로를 함께 둔다. 숫자는 품질 실험 후 조정한다.

각 청크에는 owner_id, source_type, source_id, source_version_id, title_path, text, locators, extraction_warning, embedding_model_version을 저장한다. 노트 청크는 note_revision_id 및 user_written/ai_draft/user_accepted 상태를 보존한다.

### 질문 처리

1. 인증 및 사용량 한도 확인.
2. 워크스페이스와 사용자가 선택한 범위로 허용 ID 집합 계산.
3. 현재 질문과 필요한 최근 대화만으로 검색 질의 구성.
4. 허용 집합 안에서 의미 검색과 키워드 검색을 각각 수행.
5. 순위 결합 후 중복 제거. 초기 후보 20~40개 → 필요하면 재순위화 → 최종 6~10개.
6. 문서와 개인 노트를 출처 유형별로 분리해 모델에 전달.
7. 모델은 제공된 evidence_id만 인용해 구조화 응답 생성.
8. 서버가 인용 ID 실재·권한·원문 범위를 확인하고 지원되지 않는 주장을 표시 또는 답변 재생성.
9. 답변·사용한 청크·모델·프롬프트 버전·토큰·지연시간 저장.

pgvector와 PostgreSQL 키워드 검색을 초기 후보로 사용한다 [S6]. 한국어 검색 품질은 영문 토큰화 기본 설정만으로 충족된다고 가정하지 않는다. 초기에는 제목·태그·용어 사전과 pg_trgm 등을 비교하고, 평가에서 부족할 때 한국어 분석기나 별도 검색엔진을 도입한다. 소규모에는 필터 후 정확 벡터 검색을 우선 검토한다. ANN 도입 시 필터 때문에 결과가 부족해지는 경우와 사용자별 격리를 별도 평가한다.

### 응답 규칙

- 사실·설명·사용자 생각을 구분. 개인 노트가 원문과 충돌하면 자동 병합하지 않고 양쪽을 제시한다.
- 문서에 없는 답은 “선택한 자료에서 확인하지 못함”으로 응답한다.
- 일반 배경 설명은 사용자가 허용한 모드에서만 “자료 밖 설명”으로 구분한다. 초기 기본은 자료 기반이다.
- 출처 링크 존재만으로 주장 검증 완료라고 간주하지 않는다. 인용 범위가 문장을 실제 뒷받침하는지 평가한다.
- 유사도 점수는 신뢰도 확률이 아니다. 임계값은 평가셋으로 조정하고 원점수 사용자 노출은 피한다.
- PDF·노트 속 명령은 참고 데이터로 취급한다. 문서에 “다른 사용자의 노트를 읽어라”가 있어도 도구 권한에 영향을 주지 않는다.
- 기존 AI 답변을 새 원문 사실처럼 재색인하지 않는다. 저장된 AI 노트는 출처 계보를 유지하며 확정 노트만 기본 검색에 포함한다.

## 10. 노트 작성과 자동 연결

노트 양식: 제목, 학습 목표, 핵심 개념, 나의 설명, 예시, 원문 근거, 남은 질문, 다음 학습. 자유 편집을 허용하고 필드를 강제하지 않는다.

저장은 사용자의 명시적 저장 또는 자동저장으로 revision을 만든다. 본문 변경 후 2초 지연 저장을 권장하며 마지막 저장 시간을 보여준다. index_revision과 saved_revision을 비교해 색인 대기 상태를 표시한다. AI 초안은 기존 본문에 바로 덮어쓰지 않고 미리보기·삽입·대체 선택을 제공한다.

현재 작성 문단/제목/선택한 과목으로 관련 노트를 검색한다. MVP는 버튼 요청, P1은 저장 후 5초 지연·최대 분당 2회 추천 갱신을 권장한다. 매 키 입력마다 LLM 호출하지 않는다. 동일 질의·revision 결과는 사용자·검색범위·권한 버전을 포함한 키로 캐시한다.

연결 카드: 노트 제목, 관련 문단, 연결 이유, 갱신일, 원문 근거, 열기/인용/무시. 관계 유형은 관련 개념·이전 질문·다른 설명 후보 정도로 제한한다. 선수 관계·모순은 확정 사실이 아니라 제안이다. 사용자가 수락한 연결만 note_links로 저장한다.

노트 revision을 인용하면 이후 수정해도 당시 인용은 유지하고 “새 버전 있음”을 표시한다. 최신 노트를 보여주는 일반 연결과 특정 revision에 고정된 인용을 분리한다.

## 11. 퀴즈·해설·오답 설계

입력: workspace_id, source_versions/note_revisions, 범위, 난이도, 5/10문항, 유형=단일정답 객관식. 기본 출제 근거는 PDF/Notion 원문이며 개인 노트만으로 출제할 때는 “개인 노트 기준”이라고 표시한다.

생성: 출제 범위에서 대표 개념 선택 → 근거 묶음 생성 → 문제·선택지·정답·오답 이유 생성 → 별도 검증 → 통과 문항만 제공. 출제 수를 채우기 위해 근거가 없는 문제를 만들지 않는다.

검증:
- 선택지 4개, 정답 1개, 중복 선택지 없음.
- 정답과 해설이 근거와 일치하고 다른 선택지가 정답이 될 여지가 없는지 확인.
- OCR 경고 수식·미확정 개인 가설은 기본 출제 제외.
- 질문에 정답이 노출되지 않는지, 문제끼리 정답을 알려주지 않는지 확인.
- 계산형은 제한된 지원 템플릿에 한해 결정적 계산 결과와 대조. 임의 생성 코드를 서버에서 실행하지 않는다.
- 자동 검증도 오류가 있으므로 신고·문항 무효화 기능 및 사람 평가가 필요하다.

채점은 저장된 정답 키로 수행한다. 문제 응답 API에서 제출 전 정답·해설을 보내지 않는다. 선택지 순서를 섞더라도 안정적인 option_id로 답안을 저장한다. 문제 revision·출제 근거는 고정한다. 문제 수정은 새 버전이며 과거 점수를 몰래 바꾸지 않는다.

오답 기록은 학습자가 제출한 답, 정답, 해설, 자신의 틀린 이유, 관련 노트, attempts를 가진다. 상태는 open/reviewed/retry_correct이며 완전한 개념 숙달을 의미하지 않는다. 초기 복습은 사용자 요청 재풀이, P1에서 1·3·7일 추천을 실험한다. 원문 삭제 또는 문제 오류 신고가 확인되면 affected 문제를 invalid로 바꾸고 점수 통계에서 제외한다.

## 12. Notion·삼성노트 연동

### Notion

개인 실습은 내부 연결, 다수 사용자 서비스는 OAuth 공개 연결을 사용한다 [S7]. 토큰은 서버에서 암호화 저장하고 브라우저·로그에 노출하지 않는다. OAuth state 검증과 연결 소유자 확인을 적용한다.

선택된 페이지의 블록·하위 블록을 페이지네이션해 수집한다. 지원 블록은 문단·제목·목록·인용·표·코드·수식·이미지·파일부터. 미지원 블록은 누락 사실을 보여준다. 텍스트를 합칠 때 블록 ID·경로를 유지하고 Notion 페이지/블록 원문 링크로 인용한다. PDF 페이지 번호를 만들어 붙이지 않는다.

초기에는 최대 20페이지 선택·수동 갱신. P1 자동화는 웹훅 알림 후 재조회하며 event_id로 중복 제거, 페이지별 병합 작업, last_edited_time와 content_hash로 변경 확인. 이벤트에 전체 본문이 온다고 가정하지 않는다 [S8]. 정기 상태 대조로 놓친 이벤트를 보완한다.

조회 401/403은 연결 또는 해당 리소스 검색을 중지하고 재인증을 요구한다. 404는 삭제·권한 상실 가능성으로 일단 해당 자료를 검색에서 격리한다. 429는 Retry-After 준수, 5xx는 제한된 지수 재시도. Notion 호출 제한은 요금제와 워크스페이스 공유 예산도 적용되므로 고정 초당 요청만 가정하지 않는다 [S9].

권한 철회 알림이 항상 즉시 온다는 보장은 없다. 검색에 사용할 외부 자료는 권한 확인 TTL 기본 5분을 두고, 만료 시 재검증 실패하면 검색하지 않는다. 이 설계에도 최대 TTL만큼의 지연 가능성을 문서화한다. 연결 해제는 우리 서비스에서 즉시 검색 제외하고 캐시·토큰을 폐기한다.

서비스 노트는 Notion 원본과 별개다. 자동 덮어쓰기 금지. 내보내기는 별도 P2 기능이다.

### Samsung Notes

공식 지원 경로는 PDF 저장·공유다 [S10]. 제3자 웹서비스용 전체 노트 조회 API는 이번 조사에서 확인하지 못했다. 삼성 계정 연결 또는 실시간 동기화를 제품 문구로 사용하지 않는다.

MVP는 PDF/PNG/JPEG 가져오기와 버전 교체. 필기 OCR 실패 시 사용자가 추출문을 수정하거나 해당 페이지를 검색 제외할 수 있다. 펜 스트로크·레이어·오디오 재구성은 지원하지 않는다. OneNote 피드는 일반 페이지 API 접근의 근거가 아니므로 우회 동기화 구현을 계획하지 않는다 [S11].

모바일 공유 메뉴에서 직접 받는 앱/PWA 기능은 브라우저·OS 지원을 검증한 이후 P2로 검토한다. 현재는 파일 선택 업로드로 보장한다.

## 13. 기술 구조와 선택 근거

권장 제품 구조:
브라우저 → 인증/권한이 적용된 Python API → PostgreSQL/pgvector 및 비공개 파일 저장소.
API → 작업 큐 → 문서 처리·임베딩·퀴즈 생성 워커.
API/워커 → 공통 ModelGateway → 선택한 LLM·임베딩·OCR 공급자.
Notion OAuth/웹훅 → ConnectorService → 동일 문서 파이프라인.

| 계층 | 권장안 | 이유와 대안 |
|---|---|---|
| 시제품 UI | Streamlit | 현재 골격 재사용, 빠른 전체 흐름 확인 |
| 제품 UI | React + TypeScript, Markdown 편집기, PDF.js 후보 | 원문 위치·자동저장·키보드 조작. 라이선스·버전 고정 전 확인 |
| API | FastAPI 후보, Pydantic 검증 | 기존 Python 처리 코드 재사용 |
| 관계·벡터 저장 | PostgreSQL + pgvector | 공유 관계·revision·검색 권한을 한 곳에서 관리 |
| 원문 저장 | 비공개 S3 호환 저장소 | DB에는 파일 경로·해시·메타데이터 |
| 비동기 처리 | Redis + RQ 후보 | 긴 문서 처리와 UI 분리, 단순 큐부터 |
| 문서 파싱 | Docling 우선 평가 | 구조·좌표 유지 여부를 실험 |
| 모델 | 공급자 어댑터, 설정으로 교체 | GMS/상용 API 이용 조건·품질을 따로 검증 |
| 인증 | 관리형 OIDC 또는 검증된 인증 라이브러리 | 직접 비밀번호 인증 구현 부담 축소 |

초기에는 모듈형 단일 API와 하나의 워커로 충분하다. Kubernetes, 다중 에이전트, 그래프 DB, 별도 대규모 검색 클러스터를 기본 구성에 넣지 않는다. RAGFlow는 대체 백엔드 후보이나 노트 revision·권한·퀴즈 모델까지 맡길 수 있다고 가정하지 않는다. 완성 시스템을 도입할 경우 중복 저장·권한 계층의 운영비를 먼저 비교한다.

배포 전 정확한 패키지·모델 버전과 라이선스를 잠근다. 라이브러리 코드 라이선스와 포함된 모델 가중치 라이선스는 별도로 확인한다.

제품 API 기본 경로 /api/v1. 모든 자원 조회는 인증 사용자로 범위를 제한한다. 목록은 cursor pagination. 생성 작업은 Idempotency-Key, 노트 편집은 expected_revision을 받는다.

| POST /documents/{id}/complete | hash, upload_id → 202 job_id |
| GET /jobs/{id} | stage, progress, warnings, retryable |
| POST /documents/{id}/versions | 새 파일 버전 생성 |
| POST /workspaces/{id}/document-links | document_id |
| DELETE /workspaces/{id}/document-links/{doc_id} | 연결 해제 |
| POST /workspaces/{id}/answers | question, conversation_id, scope → SSE 또는 job_id |

| POST /notes | title, body, workspace_ids → note |

응답 계약 예:
{
  "answer_id": "uuid",
  "status": "grounded",
  "segments": [
    {"text": "설명 문장", "kind": "source_fact", "citation_ids": ["uuid"]}
  ],
  "scope": {"workspace_id": "uuid", "include_linked_notes": true},
  "warnings": [],

status는 grounded/partial/insufficient_evidence/failed. citation이 있는 것과 사실 정확성이 보장되는 것은 다르다.

## 16. 안전·개인정보·자료 권한

이는 구현 통제 제안이며 법률 준수 인증이 아니다. 공개 출시 전 실제 배포 지역·약관·자료 권리 검토가 필요하다.

- 사용자별 DB 접근과 파일 경로 격리, 가능하면 DB RLS를 방어 계층으로 추가. 관리자 작업도 감사 기록.
- 객체 저장소 비공개, 짧은 만료의 서명 URL. 다운로드마다 서버 권한 확인.
- Notion 토큰 암호화, 비밀키 서버 저장, 원문·프롬프트 전문 기본 로그 금지.
- 업로드 파서 네트워크 차단·CPU/메모리/시간 제한. 문서의 URL을 자동 실행·방문하지 않음.
- 첨부파일 원격 다운로드는 허용된 공급자 호스트와 재검증된 리다이렉트만 허용. 사설 IP 접근 차단.
- 사용자 작성 Markdown·모델 출력의 HTML sanitization, 외부 스크립트 금지.
- 삭제/연결 해제 시 검색 인덱스뿐 아니라 결과 캐시·대기 작업·진행 중 생성의 권한도 무효화.
- 비용 제한은 모델 호출 전 예약하고 완료 후 정산. 동시 요청으로 한도를 우회하지 못하게 트랜잭션 사용.
- 자료를 외부 AI/OCR에 보내는 경우 처리 위치·공급자·보존 정책을 설정 화면에 안내. 실사용 개인 자료를 개발용 무료 학습 활용 조건에 무심코 전송하지 않는다.
- 강의자료는 기본 비공개. 다른 사용자에게 파일·발췌·노트를 공유하는 기능은 권리와 원문 접근 규칙을 별도 검토한 뒤 추가.
- 서비스 운영자는 “모든 자료 영구 비보존”처럼 공급자 조건으로 확인하지 않은 문구를 사용하지 않는다.

## 17. 운영, 장애, 성능 목표

다음 값은 측정 전 목표다. 기준 환경은 API 2 vCPU/4GB, 워커 4 vCPU/8GB, 관리형 DB 소규모 인스턴스와 동시 활성 사용자 10명이다. 파서 메모리 요구에 따라 워커 상향이 필요할 수 있다.

| 항목 | 목표/처리 |
|---|---|
| 일반 CRUD | p95 1초 이하 |
| 검색 | 5만 청크에서 p95 2초 이하, 권한 필터 포함 |
| 질의응답 | 대기 포함 p95 20초 이하, 장기 작업 취소 가능 |
| 노트 저장 | 저장 요청 p95 2초 이하, 실패 시 로컬 초안 유지 |
| 노트 색인 | 저장 후 p95 30초 이내, 지연 상태 표시 |
| 텍스트 PDF | 20페이지 처리 p95 120초 목표; OCR은 별도 측정 |
| 퀴즈 | 5문항 생성·검증 p95 60초 목표 |
| 복구 | 파일럿 RPO 24시간/RTO 4시간 목표, 실제 복구 연습 필수 |

작업은 at-least-once 실행을 가정하고 입력 해시·작업 유형·파서 버전으로 중복을 방지한다. 최대 3회 재시도, 중복 결과 저장 방지, lease 만료 작업 복구, 최종 실패 큐와 관리자 재시도 제공. 토큰/비용이 이미 발생한 실패는 사용자에게 알리고 무한 재생성하지 않는다.

수집 실패는 질문 기능 전체를 막지 않는다. 모델 장애 시 출처 검색·노트 편집은 계속 가능하게 한다. 임베딩 공급자 변경 시 새 인덱스를 생성·평가 후 교체하고 서로 다른 임베딩 공간을 섞지 않는다.

모니터링: 작업 실패율, 페이지 처리 시간, OCR 비율, 검색 무결과율, 근거 부족 답변율, 인용 오류, 모델별 토큰·비용, 429, DB 용량, 사용자 삭제 작업 지연. 원문 없는 request_id로 추적한다.

## 18. 비용 모델과 예산

### 확인 단가와 계산 가정

2026-10-21 확인한 공식 표의 Gemini 2.5 Flash-Lite Standard 예시 단가는 입력 USD 0.10/백만 토큰, 출력(추론 포함) USD 0.40/백만 토큰이다 [S12]. 최종 모델 선정은 아니며 해당 모델의 배포 시점 제공 여부·한국어 품질·할당량을 재확인한다. GMS 요금은 이 표에 적용할 수 없다.

Cloud Vision Document Text Detection은 월 첫 1,000단위 무료, 다음 구간 1,000단위당 USD 1.50, PDF는 페이지별 단위다 [S13]. 같은 페이지 재요청과 다른 기능 호출은 별도 비용이 될 수 있다.

월 총비용 = 서버·DB·저장·백업·전송 + 문서 처리 CPU/OCR + 임베딩 + 답변/노트/퀴즈 생성·검증 + 재시도 + 관측 도구.
원화 환산은 실제 환율 조회값 대신 예산용 1 USD=1,400원 가정을 사용한다. 세금·환율·인건비는 별도다.

### 사용자 1명당 월 사용량 가정

- 질문 100회, 회당 입력 6,000 / 출력 1,000토큰.
- 노트 초안 20회, 회당 입력 8,000 / 출력 2,000토큰.
- 퀴즈 10세트, 생성+검증 합산 세트당 입력 16,000 / 출력 4,000토큰.
- 합계 입력 920,000 / 출력 180,000토큰.
- 예시 LLM 비용: 0.92×0.10 + 0.18×0.40 = USD 0.164/사용자/월.
- 30% 재시도·부가 호출 여유 포함 USD 0.2132. 추천 검색은 기본적으로 벡터 검색이며 별도 생성 호출을 억제한다.
- 출력 가정에는 과금 대상 추론 토큰도 포함돼야 한다. 실제 reasoning 토큰이 더 많으면 비용이 상승한다.

| 시나리오 | 활성 사용자 | 위 사용량의 LLM+30% | 월 OCR 페이지 | OCR 예시 |
|---|---:|---:|---:|---:|
| 파일럿 | 10 | $2.13 | 1,000 | $0* |
| 베타 | 100 | $21.32 | 10,000 | $13.50* |
| 확대 | 1,000 | $213.20 | 100,000 | $148.50* |

* 프로젝트 전체 무료분이 남아 있다는 조건이며 사용자별 무료분이 아니다. 문서 전체 페이지 수와 OCR 대상 페이지 수는 다르다. 도표 설명·수식 VLM은 포함하지 않았다.

| 위 예시 생성 비용 | $21.32 |
| 위 예시 OCR | $13.50 |
| 임베딩·재순위화 예비비 | $5~20 |
| 관측·예비 운영비 | $10~30 |
| 소계 | $89.82~224.82 |
| 추가 20% 예비비 포함 | 약 $108~270, 가정 환율로 약 15만~38만원 |

서버·DB 범위는 실제 업체 가격 인용이 아닌 용량 계획용 가정이다. 무료 티어가 계속 유지된다고 가정하지 않는다. 모델 비용이 10배면 동일 사용량의 LLM 항목은 $213.20이 되어 총 예산도 상승한다. 1,000명 시 인프라비는 이 표를 선형 확대하지 않고 동시성·파일 크기 기준으로 재산정한다.

비용 통제: 변경된 문서만 임베딩, 동일 파일 OCR 재사용, 질문당 문맥 상한, 사용자별 생성 횟수와 공급자 월 지출 한도, OCR 사전 페이지 확인, 대량 재처리는 관리자 승인 작업. 베타 목표 월 예산 $250, 경고 70%/90%, 100%에서 새 유료 작업 차단·읽기와 편집 유지. 실제 견적이 이를 초과하면 사용자/페이지 한도를 낮춘다.

개발 인건비는 3명×6~8주=18~24인주를 기본 가정으로 별도 계산한다. 프런트/UI, 백엔드·권한, RAG·평가 역할을 나누되 매주 통합한다.

## 19. 품질 평가와 출시 기준

### 고정 평가셋

허용된 공개자료 또는 동의받은 자료 20개: 한글 텍스트 PDF 6, 영문/2단 4, 표·수식 4, 삼성노트 필기 4, Notion 페이지 2. Notion 단계 전에는 해당 항목을 제외하고 표시한다. 질문 100개: 단일 자료 40, 다중 근거 20, 이전 노트 20, 답 없음/충돌 20. 사람이 정답 근거 위치를 먼저 작성한다. 개발 조정셋과 최종 평가셋을 분리한다.

| 평가 | 베타 진입 기준 |
|---|---|
| 검색 Recall@5 | 정답 근거가 있는 질문에서 85% 이상 |
| 인용 정확성 | 표본 주장-인용 쌍 100개 중 95% 이상 실제 지지 |
| 답 없음 보류 | 근거 없는 질문 20개 중 18개 이상 보류 |
| 권한 격리 | 타 사용자/해제 자료 노출 0건, 제목·캐시 포함 |
| 원문 위치 | 텍스트 문서 표본 100개 중 95개 이상 올바른 페이지 |
| 퀴즈 | 50문항 사람 평가에서 정답·해설 타당 95% 이상, 모호 문항 제외 |
| 저장 | 재접속·동시 편집·서버 재시작에서 확정 노트 유실 0건 |
| 사용자 과제 | 10명 중 8명이 도움 없이 노트 저장·오답 복습 완료 |

소규모 표본 결과는 일반 성능 보장이 아니다. 필기·수식은 별도 성적표로 보고하며 실패율이 높으면 해당 자료 유형의 자동 출제를 비활성화한다.

### 필수 테스트 시나리오

T01 두 사용자의 동일 파일·질문에도 타인 노트 미노출.
T02 A에만 연결된 노트를 B에서 검색 불가, 연결 후 가능, 해제 즉시 불가.
T03 생성 중 자료 삭제 시 결과 보류, 캐시로 우회 불가.
T04 PDF 교체 실패 시 구버전 정상 이용; 성공 후 옛 인용은 옛 버전 유지.
T05 회전·다단 PDF 근거 페이지/좌표 확인.
T06 근거 없는 질문에 임의 출처 생성 금지.
T07 문서 내 프롬프트 주입이 검색 범위·외부 호출을 바꾸지 못함.
T08 같은 퀴즈 제출 재전송 시 중복 attempt·과금 없음.

## 20. 개발 일정과 작업 분해

### 현재 실습에 맞춘 3일 시제품

실제 사용자 인증 없이 로컬 단일 사용자 데모로 한정한다. 공개 배포와 다중 사용자 자료 업로드는 금지한다.
- 1일: step7 골격을 기반으로 PDF 추출·페이지 근거·작은 로컬 검색 연결. 사전 검증한 PDF 3개.
- 2일: SQLite에 워크스페이스·노트·연결 저장. 노트 수정·다른 공간 연결·이전 노트 검색.
- 3일: 객관식 5문항·해설·오답 저장, 전체 시연과 인용 확인.
- 제외: Notion OAuth, 손글씨 품질 보장, 자동 관련 노트, 사용자 간 공유, 정교한 PDF 하이라이트.
- 시연 완료 기준: 앱 재시작 후 노트 유지, 이전 노트 인용, 퀴즈 오답에서 근거 페이지 확인.

### 제품 MVP 6~8주, 3명 팀 가정

| 주차 | 작업 | 산출물·통과 기준 |
|---|---|---|
| 1 | 스코프·20자료 파싱 실험·화면·DB·인증 | 자료 처리 가능 범위 확정, 사용자 격리 테스트 |
| 2 | 업로드·워커·페이지·버전·기본 검색 | 재시작·중복 업로드·오류 복구 |
| 3 | 질의응답·인용·근거 평가 | 답 없음 보류, 타 사용자 누출 0 |
| 4 | 노트 저장소·revision·공간 연결·이전 노트 RAG | 핵심 연결 시나리오 완료 |
| 5 | 퀴즈 생성·검증·오답·재풀이 | 평가 50문항, 정답 키 보호 |
| 6 | 비용·삭제·부하·접근성·파일럿 | P0 출시 기준, Notion 수동 가져오기 착수 가능 |
| 7 | Notion OAuth·블록 수집·수동 갱신 | P1 연결 테스트, 실패 격리 |
| 8 | Notion 변경 동기화 또는 파일럿 개선 | 자동 동기화는 권한/중복 테스트 통과 때만 출시 |

일정이 부족하면 자동 연결·OCR 고도화·Notion 자동화를 줄인다. 근거 검증·노트 영속화·권한 격리는 줄이지 않는다. 1명 개발이면 단순히 6~8주로 약속하지 않고 통합·학습 부담을 반영해 재산정한다.

### 작업 패키지

B01 도메인/스키마/인증 → B02 업로드·버전·파싱 → B03 검색·인용 → B04 노트·revision → B05 공유·연결 추천 → B06 퀴즈·오답 → B07 운영·삭제·평가.
B08 Notion은 B02/B03/B07 이후. 모든 UI는 임시 메모리가 아닌 서비스 인터페이스로 데이터를 읽고 쓴다.

예상 신규 구조:
app.py (시제품 진입)
src/domain/ (워크스페이스·노트·퀴즈 규칙)
src/services/ (ingestion, retrieval, answers, notes, quizzes)
src/adapters/ (parser, models, notion, storage)
src/repositories/ (DB 접근·권한 필터)
src/workers/ (장기 작업)
tests/ (단위·통합·권한·평가)
docs/ (본 기획서와 결정 기록)
제품 UI/API 분리는 동일 서비스 계층을 유지하며 web/와 api/를 추가한다.

ADR-04 RAG + 관계형 모델 우선: 초기 지식 그래프 비용 회피.
ADR-05 출처 기반 객관식부터: 주관식 평가 신뢰도 문제 분리.
ADR-06 Notion 단방향·삼성 파일 가져오기: 공식 접근 경로에 맞춤.
ADR-07 교육용 시제품과 다중 사용자 제품 분리: 현재 저장소와 목표 범위의 차이 명시.
