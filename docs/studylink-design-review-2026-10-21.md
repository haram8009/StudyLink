# 기획서·아키텍처 점검 (2026-10-21)

대상: [구현기획서 v1.1](studylink-implementation-plan-v1.1.md), [아키텍처 v1](studylink-architecture.md).
상태: 문서 간 정합성과 요청·저장·재조회 흐름을 점검한 결과다. 아래 개선안은 미확정이며 구현 오류를 실행으로 재현한 결과가 아니다. 외부 서비스의 지원 모델·요금·SDK 동작은 이번 점검에서 검증하지 않았다.

## 사용자 정정 후 반영 상태

후속 지시에 따라 기존 실습 코드 재사용 전제를 철회하고, 기획서·아키텍처를 새 프로젝트 및 LangGraph 에이전트 구성 기준으로 수정했다. 아래 R1~R8은 수정 전 점검 기록이다.

- R2: 문장 단위 검증으로 결정·반영했다(인용 없는 segment 제거, 절반 넘게 제거 시 1회 재생성, 0개면 보류). 기획서 7절, 아키텍처 3.1·4.2절.
- R1: note_citations에 citation_id·source_type·대상 ID(document_id 또는 cited_note_id)를 두고 본문 `[cN]`과 짝짓는 방식으로 결정·반영했다. 저장 시 본문에 쓰인 인용만 보관한다. 기획서 5·6절, 아키텍처 4.3·5절.
- R3: `GET /api/quizzes/{id}`(제출 전 공개 문항, 제출 후 채점 결과)와 `GET /api/workspaces/{id}/answers`·`GET /api/answers/{id}`를 추가하기로 결정·반영했다. 기획서 6절, 아키텍처 3.1·7절.
- R6: 부분 생성 허용(requested_count·actual_count), 퀴즈당 1회 제출 확정·재요청 시 저장 결과 반환, 전 문항 응답 필수, attempts·reviews 단일 트랜잭션으로 결정·반영했다. 기획서 5·6·8절, 아키텍처 4.4절.
- R4: `POST /api/notes/related`(title·body·exclude_note_id, 전체 노트 범위, 서로 다른 노트 최대 3개)로 결정·반영했다. 기획서 6절, 아키텍처 3·4.3절.
- R5: 범위 SQL 후보 청크가 하나라도 있으면 질문 허용(노트만 있는 공간 포함), 없으면 400과 처리 중/근거 없음 안내 구분으로 결정·반영했다. 기획서 7절, 아키텍처 8절.
- R7: JSON 실패 처리는 그래프의 보류·fallback·문항 제외로 통일했다. P2~P5·P7은 채택하고 기획서 5·6절과 4절에 반영했다(2026-10-21). 노트 index_status는 임베딩 실패 시 예전 청크를 지워 검색에서 빼고 조회 응답으로 재저장을 안내하는 규칙으로 정했다. P1은 고정 개수 대신 관련성 기준 선택(최소 점수·상대 기준·상한 12개/약 8,000자·노트 1개 보장)으로 바꿔 채택했다.
- R8: 첫날 일정에 최소 질문·인용 화면과 답변 그래프 인용 검증을 앞당겼다. 실행 검증은 아직 하지 않았다.
- GMS 모델·크레딧 수치를 확정 근거에서 제외하고 새 환경에서 검증할 항목으로 바꿨다.
- LangGraph 상태·노드·분기·재시도 예산·영속화 경계와 GMS HTTP 어댑터·Langfuse 직접 계측을 설계했다. 공식 문서는 후속 수정에서 확인했으며, 실제 GMS 및 SDK 연동 테스트는 수행하지 않았다.

## 구현 전에 해결할 항목

### R1. [높음] 노트 저장 시 인용 식별자와 노트 출처 연결이 유실된다

- 근거: 기획서 5절 `note_citations`, 6절 초안 응답; 아키텍처 4.3절.
- 확인: 초안 본문에는 `[e1]`이 있지만 citations와 note_citations에는 대응하는 인용 ID가 없다. 노트 출처는 제목 텍스트로만 변환한다.
- 영향: `[e1]`이 노트, `[e2]`가 문서인 답변을 저장하면 배열 순서만으로 원래 번호를 복구할 수 없다. 노트 출처도 제목 중복·변경 시 원본을 식별할 수 없다.
- 제안: 노트 안에서 고유한 `citation_id`를 응답·저장·조회에 유지한다. 문서와 노트를 구분하는 `source_type` 및 대상 ID를 보존하고 본문 참조와 매핑한다. 버전 고정은 기존 계획대로 이후 단계로 둔다.
- 확인할 사례: 노트·문서 혼합 인용 초안 → 저장 → 재조회 → 각 인용에서 올바른 원본 열기.

### R2. [높음] 답변 전체에 인용 하나만 남아도 근거 없는 문장이 통과한다

- 근거: 기획서 C03·7절; 아키텍처 4.2절.
- 확인: 제공되지 않은 ID를 제거한 뒤 답변 전체 인용이 0개일 때만 보류한다. 문장별 유효 인용을 강제하는 규칙은 없다.
- 영향: 정상 인용 문장과 허위 ID 문장이 섞이면 후자는 인용만 지워진 채 grounded 답변으로 남을 수 있다.
- 제안: 각 설명 segment에 유효한 인용을 요구하고, 검증 실패 segment는 제거하거나 답변을 재생성한다. 남은 설명이 없으면 보류한다. 유효 ID가 있다는 사실과 근거가 주장을 뒷받침한다는 사실은 구분해 평가한다.
- 확인할 사례: 정상 ID와 허위 ID를 가진 두 segment 입력에서 무인용 주장이 출력되지 않는지 확인한다.

### R3. [높음] 퀴즈를 재시작·새로고침 후 복구할 조회 계약이 없다

- 근거: 기획서 6절·11절; 아키텍처 7절 `/w/:id/quiz/:quizId`.
- 확인: 생성과 제출 API는 있지만 기존 quiz_id로 문항을 조회하는 API가 없다.
- 영향: 생성 응답을 프런트 메모리에서 잃으면 기존 퀴즈 화면을 복구할 수 없다. DB 영속화만으로 재시작 완료 기준을 충족하지 못한다.
- 제안: `GET /api/quizzes/{id}`에 공개 문항·제출 상태 조회를 정의하고, 제출 후 결과 복구 방식도 정한다. 정답·해설 공개 시점을 유지한다. 질문 이력까지 복구할 것인지도 11절에서 명확히 한다.
- 확인할 사례: 생성 직후와 제출 직후 각각 서버 재시작·브라우저 새로고침으로 같은 퀴즈와 결과 복구.

### R4. [중간] 편집 중 관련 노트 검색을 현재 API와 함수로 표현할 수 없다

- 근거: 기획서 C08·6절; 아키텍처 3절 `related_notes(note_id)`, 4.3절.
- 확인: API는 저장된 note_id만 받고 편집 중 title/body를 받지 않는다. 내부 retrieve는 workspace_id가 필수지만 관련 노트의 범위는 전체 노트다.
- 영향: 신규 노트에는 ID가 없고, 기존 노트 편집 중에는 저장 전 본문으로 검색할 수 없다. 범위 구현도 담당자마다 달라질 수 있다.
- 제안: title/body와 선택적인 exclude_note_id를 받는 전체 노트 검색 계약을 별도로 정의한다. note_id로 중복을 제거해 서로 다른 노트 최대 3개를 반환한다. 응답의 `제목·문단·점수 미노출` 문구도 표시할 필드를 명시하는 형태로 정리한다.
- 확인할 사례: 미저장 노트 검색, 저장된 노트의 본문 변경 후 검색, 동일 노트 여러 청크의 중복 제거.

### R5. [중간] 연결 노트만 있는 공간을 질의응답 오류 규칙이 차단한다

- 근거: 기획서 C07·7절; 아키텍처 8절 `ready 0개면 400`.
- 확인: 검색에는 연결 노트가 포함되지만 질문 허용 여부는 ready 문서 개수만으로 판단한다.
- 영향: PDF가 없거나 처리 중이어도 연결 노트로 답할 수 있는 질문을 거절한다.
- 제안: include_notes를 반영한 전체 검색 가능 근거로 판단한다. 처리 중인 문서만 있는 경우와 근거가 전혀 없는 경우의 안내를 구분한다.
- 확인할 사례: ready 문서 0개, 검색 가능한 연결 노트 1개, include_notes=true로 정상 답변.

### R6. [중간] 퀴즈 부분 생성과 재제출 처리 계약이 빠져 있다

- 근거: 기획서 C09·5절·8절; 아키텍처 4.4절.
- 확인: C09는 5문항을 요구하지만 실패 문항은 제외한다. 1~4문항 응답 형식이 없다. attempts는 누적되고 reviews는 question_id 단위지만, 어느 attempt를 오답의 '내 답'으로 보여줄지 정하지 않았다.
- 영향: 화면이 5문항을 전제하거나 재제출 결과와 오답 목록이 서로 달라질 수 있다. 다른 퀴즈의 question_id, 누락 답안, 유효하지 않은 option_id 처리도 구현자 판단에 맡겨져 있다.
- 제안: requested_count/actual_count와 부분 성공 안내를 정한다. 시제품에서는 최초 제출만 확정하고 동일 제출 재요청은 같은 결과를 반환하는 방식 등을 선택한다. 제출 유효성 검증 후 attempts·reviews를 한 트랜잭션으로 기록한다. 재풀이를 허용한다면 reviews가 가리키는 시도를 명시한다.
- 확인할 사례: 3개만 생성, 중복 제출, 다른 퀴즈 문항 제출, 잘못된 선택지 제출.

## 문서 계약과 일정 보완

### R7. [중간] 미채택 제안이 본문에서는 구현 전제로 사용된다

- 근거: 아키텍처 0절·12절과 2~8절; 기획서 5~7절·12절.
- 확인: P1~P5·P7은 채택 전인데 문서4+노트2, retry, MOCK_LLM 등이 본문에 반영돼 있다. 기획서에는 단일 top-6과 retry 없는 API가 남아 있다. embedding_dim과 index_status도 아키텍처에만 있으며, JSON 파싱 실패는 기획서의 일반 텍스트 반환과 아키텍처의 insufficient_evidence가 다르다.
- 제안: 채택한 항목만 두 문서의 스키마·API·오류 계약에 함께 반영한다. 노트 index_status는 응답뿐 아니라 재조회·실패 후 검색 포함 여부를 정의한다. 임베딩 실패 시 구 청크를 남기는지 지우는지, 변경된 본문과 어긋난 청크를 어떻게 제외하는지도 정한다.

### R8. [중간] 첫날 통합 목표의 선행 작업이 둘째 날에 배치돼 있다

- 근거: 기획서 10절.
- 확인: 첫날 종료 목표는 페이지 인용 답변이지만 질의응답·PDF 페이지 화면과 인용 검증은 둘째 날 오전에 배치돼 있다.
- 제안: 첫날에 최소 질문 입력·답변·인용 클릭 화면과 최소 인용 검증을 앞당기거나, 첫날 완료 기준을 API 통합으로 명시한다. C08 축소 여부는 둘째 날 통합 실패 후보다 API 계약 확정 시에 판단하는 편이 일정 위험을 줄인다.

## 추가 확인 항목

- QA·초안 10초, 퀴즈 30초는 목표로 유지한다. 실측(생성 1회 약 1.4~1.6초) 후 HTTP 타임아웃 20초, 요청 한도 질의응답 30초·초안 20초·퀴즈 45초로 정했다(2026-10-21).
- GMS 호출은 2026-10-21에 확인했다(gpt-4o-mini JSON schema 지원, text-embedding-3-small 1536차원, 아키텍처 12절). 크레딧 단위와 한도는 여전히 미확인이다.
- GMS 크레딧 숫자에는 과금 단위·확인 출처가 없다. 현재 수치의 오류 여부는 미검증이며, 비용 판단 근거로 쓰려면 단위를 기록해야 한다.
- 모델 교체 후 전체 재임베딩 실행 방법과 MOCK_LLM 벡터가 실제 벡터와 섞이지 않는 방법을 정한다. → 기존 설계로 해결: 검색 SQL이 `embedding_model`이 현재 설정과 같은 청크만 읽고, 목 모드는 별도 DB 파일을 쓴다(아키텍처 4.2·6절). 전체 재임베딩은 1일차에 문서·노트를 다시 수집하는 관리 스크립트로 만든다.
- 재시작 복구·인용 매핑·문장별 검증·노트만 있는 공간·부분 퀴즈를 통합 확인 항목에 포함한다. → 아키텍처 12절 체크리스트에 추가함(2026-10-21).

## 평가

로컬 단일 사용자·소규모 자료라는 전제에서 계층과 저장 구조는 과도하게 복잡하지 않다. 다만 핵심 차별점인 출처 추적과 노트 검색을 실제로 연결할 계약에 빈틈이 있다. R1~R3을 먼저 정리하고, R4~R8을 첫날 계약 확정에 반영하는 순서를 제안한다. 이번 점검으로 기존 제안의 채택 여부를 변경하지 않았다.
