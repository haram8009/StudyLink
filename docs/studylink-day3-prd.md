# StudyLink 3일차 PRD — 퀴즈·오답노트와 시제품 마무리

작성일: 2026-10-22 (Asia/Seoul)
상태: 구현용 요구사항. 퀴즈·채점·오답·노트 초안·관련 노트·평가 도구는 구현되었다([3일차 통합 기록](day3-integration.md)). 평가의 답 없음 보류·데모 4단계 노트 인용 목표와 사람 판정·데모 리허설은 미완료다.
기준: [구현기획서 v1.1](studylink-implementation-plan-v1.1.md) 3·6·8·10·11·12절, [아키텍처](studylink-architecture.md) 3.1·4.4·6·7절, [2일차 PRD](studylink-day2-prd.md), [2일차 통합 기록](day2-integration.md), [ADR 0001](adr/0001-langgraph-without-langchain.md), [ADR 0002](adr/0002-workspace-chats-shared-resources.md), [용어집](../CONTEXT.md).

## Problem Statement

> 후속 요구(2026-10-22): 퀴즈 문항 수·난이도 선택, 탈락 문항 보충, 정답·해설의 참고 자료 표시는 [퀴즈 변경 PRD](quiz-customization-prd.md)를 따른다. 이 문서의 5문항 고정·부분 생성 성공 요구는 해당 PRD로 대체한다. 기존 구현 기록과 그 밖의 3일차 범위는 유지한다.

학습자는 워크스페이스의 자료로 질문하고 답변을 확인할 수 있게 되었지만, 실제로 이해했는지 스스로 점검할 방법이 없다. 읽고 질문하는 것만으로는 무엇을 모르는지 드러나지 않는다. 시판 퀴즈 도구는 문제를 만들어 주더라도 틀린 문제가 원문 어디에서 나왔는지, 내가 정리한 노트 중 무엇을 다시 봐야 하는지 알려주지 않는다.

또한 시제품의 핵심 흐름 중 일부가 아직 끊겨 있다. 답변을 노트로 옮기려면 직접 다시 써야 하고(노트 초안 미구현), 노트를 편집하면서 관련된 이전 노트를 찾기 어렵다(관련 노트 미구현). 검색 품질 목표(답 있음 8/10, 답 없음 4/5)를 측정한 적이 없어 데모 질문에서 노트가 실제로 인용되는지도 확인되지 않았다. 마지막 날에 이 공백을 메우지 않으면 데모 시나리오 2·5·6단계를 보여줄 수 없다.

## Solution

**3일차 완료 흐름은 워크스페이스 자료로 퀴즈 생성 → 풀이·제출 → 채점·해설 → 오답노트에서 근거 페이지와 관련 노트로 이동 → 틀린 이유 메모다.** 함께 2일차에서 넘어온 노트 초안·관련 노트·평가 도구를 마무리하고, 데모 시나리오 1~6을 앱 재시작 후에도 끊김 없이 리허설한다.

퀴즈는 워크스페이스 단위다. 어느 채팅에서 공부했든 같은 워크스페이스의 처리 완료 자료에서 출제한다. 문항마다 근거 자료·페이지가 붙고, 제출 전에는 정답과 해설을 보여주지 않는다. 제출은 한 번으로 확정되며 틀린 문항은 **오답**으로 쌓인다. 오답을 열면 그 문항의 근거 페이지를 PDF 패널에서 열고, 문제·정답과 관련된 내 노트를 찾아 열 수 있다.

모델이 만든 문항은 코드로 검증해 형식이 맞지 않거나 근거가 없는 문항을 제외한다. 일부만 만들어지면 만들어진 만큼만 내고 그 사실을 알린다. 문항을 하나도 만들지 못하면 근거 없는 문제로 채우지 않고 실패를 알린다.

## User Stories

### 퀴즈 생성

1. 학습자로서, 워크스페이스 화면에서 퀴즈를 만들고 싶다. 공부한 자료를 이해했는지 점검하기 위해서다.
2. 학습자로서, 어느 채팅에 있든 같은 워크스페이스 자료로 퀴즈를 만들고 싶다. 퀴즈가 특정 대화가 아니라 과목 전체를 다루게 하기 위해서다.
3. 학습자로서, 한 번에 5문항 4지선다 퀴즈를 받고 싶다. 짧은 시간에 핵심을 확인하기 위해서다.
4. 학습자로서, 문항이 자료의 서로 다른 페이지에서 고루 나오길 원한다. 한 부분만 반복해서 묻지 않게 하기 위해서다.
5. 학습자로서, 처리 완료된 자료에서만 출제되길 원한다. 아직 읽히지 않은 자료로 엉뚱한 문제가 나오지 않게 하기 위해서다.
6. 학습자로서, 퀴즈 생성 중 진행 상태를 보고 싶다. 오래 걸려도 멈춘 것이 아님을 알기 위해서다.
7. 학습자로서, 생성 버튼을 여러 번 눌러도 퀴즈가 중복으로 만들어지지 않길 원한다. 같은 퀴즈가 쌓이지 않게 하기 위해서다.
8. 학습자로서, 5문항을 다 만들지 못했을 때 "N문항만 만들었습니다" 안내를 보고 싶다. 퀴즈가 짧은 이유를 알기 위해서다.
9. 학습자로서, 출제할 자료가 없으면 자료를 먼저 올리라는 안내를 받고 싶다. 무엇을 해야 하는지 알기 위해서다.
10. 학습자로서, 문항을 하나도 만들지 못했을 때 다시 시도하라는 안내를 받고 싶다. 근거 없는 문제를 받지 않기 위해서다.
11. 학습자로서, 모델 서비스 장애 시 일시적 오류 안내를 받고 싶다. 내 자료 문제와 구분하기 위해서다.
12. 학습자로서, 선택지 중 정답 위치가 한쪽으로 몰리지 않길 원한다. 문제를 읽지 않고 찍어서 맞히지 않기 위해서다.

### 풀이와 제출

13. 학습자로서, 제출 전에는 정답과 해설이 화면이나 응답 어디에도 드러나지 않길 원한다. 공정하게 스스로를 점검하기 위해서다.
14. 학습자로서, 문항마다 근거 자료 이름과 페이지를 미리 보고 싶다. 어느 부분을 묻는지 알고 풀기 위해서다.
15. 학습자로서, 문항마다 하나의 선택지를 고르고 바꿀 수 있길 원한다. 제출 전까지 답을 고치기 위해서다.
16. 학습자로서, 답하지 않은 문항이 있으면 제출 전에 알림을 받고 싶다. 실수로 빠뜨리지 않기 위해서다.
17. 학습자로서, 풀이 중 새로고침해도 퀴즈 문항을 다시 열고 싶다. 처음부터 다시 만들지 않기 위해서다.
18. 학습자로서, 제출하면 바로 점수와 문항별 정오를 보고 싶다. 어디가 약한지 즉시 알기 위해서다.
19. 학습자로서, 제출 후 문항별로 내 답·정답·해설을 보고 싶다. 왜 틀렸는지 이해하기 위해서다.
20. 학습자로서, 채점 결과에서 근거 페이지를 눌러 PDF 패널로 열고 싶다. 해설을 원문과 대조하기 위해서다.
21. 학습자로서, 제출을 두 번 눌러도 결과가 바뀌지 않길 원한다. 채점 기록이 중복되거나 뒤바뀌지 않게 하기 위해서다.
22. 학습자로서, 제출한 퀴즈를 나중에 다시 열면 채점 결과가 그대로 보이길 원한다. 지난 점검 결과를 확인하기 위해서다.
23. 학습자로서, 워크스페이스의 최근 퀴즈 목록을 보고 싶다. 풀던 퀴즈나 지난 결과로 돌아가기 위해서다.
24. 학습자로서, 같은 문제를 다시 풀고 싶으면 새 퀴즈를 만들고 싶다. 제출한 퀴즈의 기록을 덮어쓰지 않기 위해서다.

### 오답노트

25. 학습자로서, 워크스페이스의 오답 목록을 보고 싶다. 복습할 문제를 한곳에서 확인하기 위해서다.
26. 학습자로서, 오답마다 문제·내 답·정답·해설을 보고 싶다. 틀린 이유를 다시 떠올리기 위해서다.
27. 학습자로서, 오답의 근거 페이지를 눌러 해당 PDF 페이지를 열고 싶다. 원문으로 바로 돌아가기 위해서다.
28. 학습자로서, 오답을 열면 문제와 정답에 관련된 내 노트를 최대 3개 보고 싶다. 내가 정리한 내용으로 복습하기 위해서다.
29. 학습자로서, 관련 노트를 눌러 노트 미리보기로 열고 싶다. 노트와 오답을 나란히 보기 위해서다.
30. 학습자로서, 관련 노트가 없을 때 "관련 노트 없음"과 노트 작성 안내를 보고 싶다. 빈 화면에서 다음 행동을 알기 위해서다.
31. 학습자로서, 오답마다 틀린 이유를 메모하고 싶다. 같은 실수를 반복하지 않기 위해서다.
32. 학습자로서, 복습을 마친 오답을 "복습함"으로 표시하고 싶다. 남은 복습만 골라 보기 위해서다.
33. 학습자로서, 오답 목록을 복습 전/복습함으로 걸러 보고 싶다. 남은 일을 먼저 처리하기 위해서다.
34. 학습자로서, 앱을 다시 시작해도 오답·메모·복습 상태가 남아 있길 원한다. 복습을 이어가기 위해서다.

### 2일차 이월: 노트 초안·관련 노트

35. 학습자로서, 근거 답변에서 "노트로 만들기"를 눌러 요약 초안을 받고 싶다. 핵심을 다시 쓰는 수고를 줄이기 위해서다.
36. 학습자로서, 초안의 인용이 원 답변의 근거로만 제한되길 원한다. 새로 지어낸 출처를 믿지 않기 위해서다.
37. 학습자로서, 요약이 실패해도 답변을 옮긴 초안과 그 사실 안내를 받고 싶다. 노트 작성을 계속하기 위해서다.
38. 학습자로서, 근거 부족 답변에서는 초안 만들기가 막히길 원한다. 확인되지 않은 내용을 노트로 옮기지 않기 위해서다.
39. 학습자로서, 초안을 편집해 저장하고 현재 워크스페이스에 바로 연결하고 싶다. 저장한 노트를 다른 채팅에서 곧바로 활용하기 위해서다.
40. 학습자로서, 노트 편집 중 버튼을 눌러 관련된 이전 노트 최대 3개를 보고 싶다. 흩어진 정리를 서로 잇기 위해서다.
41. 학습자로서, 관련 노트 검색이 저장하지 않은 내용으로도 동작하되 그 내용을 저장하지 않길 원한다. 편집 중 미리 찾아보기 위해서다.

### 데모·품질

42. 시연자로서, 데모 시나리오 1~6을 앱 재시작 후에도 끊김 없이 진행하고 싶다. 핵심 차별점을 안정적으로 보여주기 위해서다.
43. 시연자로서, Langfuse에서 질의응답·노트 초안·퀴즈 생성 trace를 보여주고 싶다. 근거·프롬프트·토큰이 추적됨을 증명하기 위해서다.
44. 개발자로서, 평가 질문 15개의 결과를 CSV로 받아 사람이 판정하고 싶다. 검색 품질 목표 달성 여부를 근거로 판단하기 위해서다.
45. 개발자로서, 생성된 퀴즈 10문항을 사람이 검토해 정답·해설 오류를 세고 싶다. 퀴즈 품질 목표(오류 1개 이하)를 확인하기 위해서다.

## Implementation Decisions

### 우선순위

| 순위 | 항목 | 이유 |
| --- | --- | --- |
| P0 | 퀴즈 생성·풀이·제출·채점, 오답 목록·근거 페이지 이동 | 데모 5단계, 축소하지 않는 "오답에서 원문 이동" |
| P0 | 관련 노트 검색 모듈 | 오답의 관련 노트와 C08이 함께 쓴다. 오답 → 노트 이동(차별점 2)에 필요 |
| P0 | 노트 초안 | 데모 2단계 |
| P0 | 평가 도구와 15문항 판정, 퀴즈 10문항 검토 | 완료 기준 측정 |
| P1 | 틀린 이유 메모·복습 상태 | 기획서 축소안상 시간 부족 시 제외 가능 |
| P2 | 노트 편집 중 관련 노트 버튼(C08 화면) | 축소안에서 가장 먼저 제외. 검색 모듈은 P0로 유지 |
| 스트레치 | 오답 재풀이(새 퀴즈 생성), PDF 하이라이트, BM25 | 시간 여유 시 |

3일 오전 첫 작업은 기존 규칙대로 2일차 통합 흐름(노트 저장 → 다른 워크스페이스 연결 → 노트 인용)을 실제 데모 자료로 확인하는 것이다. 동작하지 않으면 새 기능보다 먼저 고친다.

| 오답 서비스 | 목록·단건·수정 | 워크스페이스 범위, 상태 필터, 메모·상태 갱신, 문항·채점 정보 조합 | B |
| 관련 노트 검색 | `related_notes(text, exclude_note_id=None, k=3)` | 색인 성공 전체 노트 대상, 노트별 최고 점수 청크 하나, 자기 자신 제외, 점수 비노출, 입력 미저장 | C 검색, B HTTP |
| 노트 초안 그래프·서비스 | `draft_note(answer_id)` | 원 답변 조회, 요약·인용 검증·1회 재생성, `[eN]`→`[cN]` 재번호화, 20초 예산, 결정적 fallback, DB 미저장 | C 그래프, B HTTP |
| 평가 도구 | 질문셋 입력 → 판정용 CSV | `answer_question` 직접 호출, 근거 수·점수·노트 보장·재검색·상태·인용 페이지·trace ID, 기대 페이지·보류 자동 비교, 사람 판정란 | C |
| 퀴즈·오답·초안 화면 | 위 HTTP 계약 | 생성 진행·중복 방지, 풀이 상태, 새로고침 복구, 채점 표시, 오답 필터·메모, PDF 패널·노트 미리보기 재사용 | A |

깊은 모듈 원칙: 채점 서비스와 출제 근거 선택은 모델 호출 없이 입력 → 결과로 검증할 수 있는 단순한 계약 뒤에 트랜잭션·멱등성·샘플링 규칙을 감춘다. 관련 노트 검색은 오답 화면과 노트 편집 화면이 같은 모듈을 쓰며, 각 화면에 검색 규칙을 따로 두지 않는다. 기존 React·FastAPI·SQLite·LangGraph·GMS 어댑터 구성을 유지하고 LangChain을 쓰지 않는다(ADR 0001).

### 워크스페이스·채팅과의 관계

- 퀴즈와 오답은 워크스페이스에 속하고 채팅에는 속하지 않는다. ADR 0002의 공통 자원 원칙에 따라 어느 채팅에서 진입해도 같은 퀴즈 목록·오답노트를 본다.
- 출제 범위는 워크스페이스의 ready 자료다. 연결 노트와 대화 기록은 출제 근거로 쓰지 않는다. 노트는 오답의 관련 노트로만 등장한다.
- 오답 화면의 근거 페이지와 관련 노트는 기존 공통 자원 패널의 PDF 뷰어·노트 미리보기를 재사용한다.

### HTTP 계약

| 기능 | 계약과 기대 동작 |
| --- | --- |
| 퀴즈 생성 | `POST /api/workspaces/{id}/quizzes` body `{count}`(기본 5, 1~5) → 201, `{quiz_id, workspace_id, requested_count, actual_count, created_at, submitted_at: null, questions: [QuestionPublic]}` |
| 최근 퀴즈 | `GET /api/workspaces/{id}/quizzes` → 최근 20개 `{quiz_id, requested_count, actual_count, created_at, submitted_at, score}`. 제출 전 score는 null |
| 퀴즈 조회 | `GET /api/quizzes/{id}` → 제출 전 QuestionPublic 목록, 제출 후 채점 결과(제출 응답과 같은 형식) |
| 제출 | `POST /api/quizzes/{id}/submit` body `{answers: {question_id: option_id}}` → `{quiz_id, score, total, submitted_at, questions: [QuestionGraded]}` |
| 오답 목록 | `GET /api/reviews?workspace_id=&status=` → `[{review_id, quiz_id, question_id, stem, selected_option_id, answer_option_id, options, explanation, document_id, filename, page, quote, status, learner_reason, created_at}]`. 관련 노트는 포함하지 않는다 |
| 오답 단건 | `GET /api/reviews/{id}` → 목록 항목 + `related_notes: [{note_id, title, snippet, linked}]` 최대 3개. linked는 현재 워크스페이스 연결 여부 |
| 오답 수정 | `PATCH /api/reviews/{id}` body `{learner_reason?, status?}` → 오답 단건(related_notes 제외) |
| 노트 초안 | `POST /api/answers/{id}/note-draft` → `{title, body, citations, fallback}`. DB 저장 없음. 근거 부족 답변 422 |
| 관련 노트 | `POST /api/notes/related` body `{title, body, exclude_note_id?}` → `[{note_id, title, snippet}]` 최대 3개 |

- QuestionPublic: `{question_id, stem, options: [{option_id, text}], document_id, filename, page}`. 정답 option_id·해설·발췌를 넣지 않는다.
- QuestionGraded: QuestionPublic + `{selected_option_id, answer_option_id, correct, explanation, quote}`.
- 공개용·채점용 응답은 서로 다른 Pydantic 모델로 정의해 정답 누출을 필드 누락 실수가 아니라 타입으로 막는다(아키텍처 4.4절).
- 오류: 출제할 ready 자료·후보 청크 없음 400, 없는 워크스페이스·퀴즈·오답 404, 같은 워크스페이스 퀴즈 생성 중 재요청 409, 유효 문항 0개 422, 제출 입력 오류 422(아무것도 저장하지 않음), 공급자 전체 장애 503. 기존 `{detail}` 형식을 유지한다.
- 관련 노트를 오답 단건에서만 계산하는 것은 목록 조회마다 임베딩 호출이 오답 수만큼 생기는 것을 피하기 위해서다. "저장하지 않고 조회 시 즉석 계산"이라는 아키텍처 4.4절 원칙은 그대로다.

### 퀴즈 생성 규칙

- 근거 선택: 워크스페이스 ready 자료의 doc 청크 중 200자 이상을 후보로 하고, 가능한 한 서로 다른 페이지에서 count개를 무작위로 고른다. 후보가 count보다 적으면 있는 만큼만 출제한다.
- 문항 생성: 근거마다 독립 문항 분기를 Send로 실행한다(동시 최대 5). 모델은 문제·선택지 4개·정답 표시·해설만 출력하고, 자료 ID·페이지·발췌는 근거 청크에서 서버가 채운다.
- 검증(코드): 스키마, 선택지 정확히 4개, 공백·중복 선택지 없음, 정답이 선택지 중 하나, 해설 비어 있지 않음. 실패 문항은 1회 재생성하고 그래도 실패하면 제외한다. 근거 없는 문항으로 개수를 채우지 않는다.
- 선택지 순서: 검증 통과 후 서버가 선택지 순서를 섞고 option_id를 다시 매긴다. 모델의 정답 위치 편향이 그대로 드러나지 않게 한다.
- 부분 생성: 유효 문항이 1~4개면 저장하고 requested_count·actual_count로 안내한다. 0개면 422. 모든 분기가 공급자 장애로 끝나면 503.
- 예산: 요청 전체 45초. 남은 시간이 부족한 분기는 시작하지 않거나 제외하고 부분 생성 규칙을 적용한다. 목표 지연은 30초다.
- 저장: 그래프가 끝난 뒤 서비스가 quizzes·questions를 한 트랜잭션으로 저장한다. 재시도 노드 안에서 DB 쓰기를 하지 않는다.
- 동시성: 같은 워크스페이스의 퀴즈 생성 중 재요청은 409로 거절한다(프로세스 내 잠금, 채팅 ask와 같은 방식). 다른 워크스페이스는 서로 막지 않는다.
- 관측: root trace `quiz_generate` 아래 근거 선택·문항 분기별 생성·검증·재시도·제외 사유·선택 chunk_id를 기록한다. 프롬프트 버전은 `quiz-v1`로 시작한다. 루트 관측을 연 상태에서 그래프를 실행해 Send 분기가 한 trace로 묶이게 한다.

### 제출·채점 규칙

- 퀴즈당 한 번 제출로 확정한다. 모든 문항에 답해야 하고 question_id·option_id는 해당 퀴즈의 것이어야 한다. 어긋나면 422이며 아무것도 저장하지 않는다.
- 이미 제출한 퀴즈의 재제출은 채점하지 않고 저장된 attempts로 결과를 재구성해 200으로 돌려준다.
- 한 트랜잭션에서 `submitted_at IS NULL`일 때만 갱신하고 attempts insert와 오답 reviews insert(question_id UNIQUE, status=open)를 함께 커밋한다. 갱신 행이 0이면 동시 제출로 보고 저장된 결과를 반환한다.
- 채점은 모델을 호출하지 않는다.

### 오답 규칙

- 틀린 문항마다 reviews 1행(status=open). 맞힌 문항은 오답이 아니다.
- learner_reason은 최대 2,000자. status는 open ↔ reviewed로 바꿀 수 있다.
- 관련 노트 질의는 "문제 + 정답 선택지 텍스트"다. 범위는 색인 성공 전체 노트이며, 현재 워크스페이스 연결 여부를 linked로 표시한다. 연결되지 않은 노트를 열 수 있지만 자동으로 연결하지 않는다.
- 근거 자료가 이후 실패 상태가 되거나 파일이 없으면 페이지 이동 대신 "원문을 열 수 없음"을 표시하고 오답 기록은 유지한다.

### 스키마 변경

- questions에 `quote`(근거 청크 발췌)와 `chunk_id`(출제 근거 청크)를 추가한다. 오답 화면이 발췌를 보여주고 평가·디버깅에서 출제 근거를 추적하기 위해서다. 기존 DB는 컬럼 존재 검사 후 ALTER TABLE로 추가한다(2일차 answers.chat_id와 같은 방식).
- quizzes는 기존대로 workspace_id에 속하며 chat_id를 두지 않는다.
- 조회용 인덱스: `questions(quiz_id)`, `quizzes(workspace_id)`, `attempts(question_id)`.

### 노트 초안·관련 노트(2일차 PRD 계약 유지)

- 초안은 저장된 grounded 답변을 요약하고 원 답변 인용 범위로 검증한다. 출력 검증 실패는 1회 재생성, 최종 실패·공급자 장애·20초 예산 소진 시 원 답변의 유효 문장을 문단으로 옮기는 결정적 fallback을 `fallback: true`로 돌려준다. 프롬프트 버전은 `note-draft-v1`, trace는 `note_draft`.
- 초안 화면은 기존 노트 작성 UI를 재사용하고, 저장 시 기본 연결 대상은 답변이 속한 워크스페이스다.
- 관련 노트는 버튼을 누를 때만 저장 전 제목·본문으로 검색하고, 검색 때문에 본문을 저장하지 않는다.

### 화면

- 워크스페이스 화면 상단에 "퀴즈"와 "오답노트" 진입점을 둔다. 채팅 목록·공통 자원 패널 구조(2일차)는 유지한다.
- 퀴즈 화면(`/w/:id/quiz/:quizId`): 문항·선택지·근거 자료·페이지 표시, 미응답 표시, 제출 후 정오·정답·해설·발췌, 근거 페이지 클릭 시 PDF 패널. 새로고침 시 퀴즈 조회로 복구한다.
- 퀴즈 생성 중에는 버튼을 비활성화하고 진행 상태를 표시한다. 부분 생성이면 "N문항만 만들었습니다"를 표시한다.
- 오답노트(`/w/:id/reviews`): 복습 전/복습함 필터, 오답 열기 시 관련 노트 로딩, 틀린 이유 메모 저장, 근거 페이지·관련 노트 열기.
- 답변별 "노트로 만들기"는 근거 부족 답변에서 비활성화한다. fallback이면 "요약 없이 답변을 옮겨 담음"을 표시한다.
- 목 모드는 퀴즈 생성(정상·부분 생성·0문항·공급자 장애)·제출·오답·초안·관련 노트까지 확장해 백엔드 없이 전 흐름을 확인할 수 있게 한다.

## Testing Decisions

좋은 테스트는 공개 서비스 함수·HTTP 응답과 저장 후 재조회 결과를 검증한다. 내부 노드 호출 순서나 SQL 문자열을 복제하지 않는다. 모델 호출은 GMS 대역, 임베딩은 결정적 벡터로 대체하고 실제 GMS·Langfuse 실측은 자동 테스트와 분리한다. 화면은 목 모드와 실제 API로 수동 통합 검증한다.

| 대상 | 검증할 외부 동작 |
| --- | --- |
| 출제 근거 선택 | ready 자료만, 200자 미만 제외, 서로 다른 페이지 우선, 다른 워크스페이스·노트 청크 제외, 후보 부족 시 있는 만큼, 후보 0개 400 |
| 퀴즈 생성 | 정상 5문항, 문항 검증 실패 후 재생성 성공, 재생성 소진 시 제외와 actual_count, 0문항 422, 전체 공급자 장애 503, 자료 ID·페이지가 모델 출력이 아닌 근거에서 채워짐, 선택지 섞기 후 정답 ID 일관성, 그래프 실패 시 DB 미저장, 같은 워크스페이스 동시 생성 409 |

| 평가 도구 | 대역 모드에서 CSV 열·자동 비교 값 생성 |
| 회귀 | 기존 1·2일차 테스트 48개 유지 |

선례: 임시 SQLite와 FastAPI TestClient를 쓰는 API 테스트(1일차 백엔드, 2일차 채팅·노트 API), GMS 대역과 결정적 벡터를 쓰는 검색·답변 그래프 테스트(1일차 에이전트, 2일차 문맥·재검색), httpx 대역을 쓰는 어댑터 테스트. 같은 방식으로 3일차 API·그래프 테스트 파일을 추가한다.

### 3일차 인수 시나리오

1. "자연어처리 기초"에서 퀴즈를 만들어 5문항을 받는다. 제출 전 응답에 정답·해설이 없고, 문항마다 자료·페이지가 표시된다.
2. 일부러 1~2문항을 틀려 제출한다. 점수·정오·해설·발췌가 보이고, 근거 페이지 클릭 시 PDF 패널이 해당 페이지로 열린다.
3. 제출을 다시 보내도 결과가 같고 오답이 중복되지 않는다.
4. 오답노트에서 오답을 열어 근거 페이지와 관련 노트("기울기 소실 정리" 등)를 연다. 틀린 이유를 메모하고 복습함으로 바꾼 뒤 필터로 확인한다.
5. 다른 채팅으로 전환해도 같은 퀴즈 목록·오답노트가 보인다.
6. 서버 재시작·새로고침 후 퀴즈 결과·오답·메모가 유지된다. 풀이 중이던 퀴즈도 다시 열린다.
7. 문항 출력 오류·공급자 장애를 목 시나리오로 주입해 부분 생성 안내, 0문항 422, 503 안내를 확인한다.
8. 답변에서 노트 초안을 만들어 "기울기 소실 정리"로 저장하고, "LLM" 워크스페이스에 연결해 데모 4단계 질문에서 노트 인용을 확인한다.
9. 평가 15문항 CSV를 사람이 판정해 답 있음 8/10·답 없음 4/5 달성 여부를 기록한다. 퀴즈 10문항 오류 수를 기록한다.
10. 데모 시나리오 1~6을 앱 재시작 후 2회 리허설하고 Langfuse에서 ask·note_draft·quiz_generate trace를 연다.

인수 항목은 실제 실행 후에만 완료로 표시하고 목 모드 통과와 실제 GMS 통과를 구분해 기록한다.

## Out of Scope

- 로그인·다중 사용자, 공개 배포, Notion·삼성노트 연동, OCR·스캔 PDF, 사용자 간 공유, 비용 한도.
- 노트·연결 노트·대화 기록을 출제 근거로 쓰는 퀴즈, 객관식 외 문항 형식, 문항 수 사용자 지정 5 초과, 난이도 조절.
- 같은 퀴즈 재제출, 간격 반복(spaced repetition) 일정, 오답 자동 재출제. 오답 재풀이는 스트레치이며 새 퀴즈 생성으로만 만든다.
- 퀴즈·오답 삭제, 채팅 이름 변경·삭제, 장기 문맥 요약(ADR 0002 범위 제외 유지).
- 노트 삭제·revision, 미저장 초안 자동 저장·복구, 자동 관련 노트 갱신.
- 다중 프로세스 환경의 409 잠금, 엄격한 wall-clock 중단 보장.
- PDF 문장 하이라이트·BM25 결합·벡터 DB 교체(스트레치 또는 이후 단계).

### 문서와 결정 기록

- 이 PRD의 최신본은 제품 저장소 docs에 둔다. 실습 저장소에는 링크만 남긴다.
- 이슈 트래커가 없으므로 외부 게시·ready-for-agent 라벨 적용은 하지 않았다. 트래커가 정해지면 이 문서를 근거로 게시한다.
- 이 PRD에서 새로 정한 사항: 퀴즈·오답의 워크스페이스 소속(채팅 무관), 최근 퀴즈 목록 API, 오답 관련 노트의 단건 계산, questions의 quote·chunk_id 추가, 선택지 순서 섞기, 같은 워크스페이스 퀴즈 생성 409. 기획서 6절과 아키텍처 4.4·7절에 함께 반영한다. 되돌리기 어려운 결정은 아니라 ADR은 만들지 않았다.
- 2일차 미완료(노트 초안·관련 노트·평가)는 이 PRD로 이월했다. 2일차 PRD의 해당 계약은 그대로 유효하다.
